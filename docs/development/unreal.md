Engine: **Unreal Engine 5.8.x**, locked to **5.8.4** (latest stable hotfix 2026-10-20; 5.9 is only a preview),
installed with the Epic Games Launcher. A source build of the engine is not needed for a client game (a dedicated
server would need one; not planned).

The editor and its Python tests only need the installed engine. The packaging workstation also has the UE 5.8 Windows toolchain (Epic's
[Visual Studio setup](https://dev.epicgames.com/documentation/unreal-engine/setting-up-visual-studio-development-environment-for-cplusplus-projects-in-unreal-engine)

- Visual Studio 2022 **17.14+** or Visual Studio 2026 (18.x) with the *Game development with C++*,
  *Desktop development with C++* and *.NET desktop development* workloads;
- MSVC v143 **14.38+** (14.50 recommended), Windows SDK **10.0.22621.0+**, .NET Framework 4.6.2 targeting pack;
- UnrealBuildTool runs on the .NET SDK bundled with the engine; a system .NET is not required.

The development PC (i9-10900K, RTX 3080, 32 GB RAM, Windows 11 Pro) is above Epic's recommendation for the editor.

   ```text

   ```

   (or *Visual Studio Installer → More → Import configuration* for an existing install). The file selects the
   CoreEditor, NativeGame (*Game development with C++*), NativeDesktop (*Desktop development with C++*) and
   ManagedDesktop (*.NET desktop development*) workloads, MSVC v143 x64/x86, Windows 11 SDK 22621, the

missing are listed for information; Unreal-specific VS components are never checked.

## Version lock

- `EngineAssociation: "5.8"` in `Lunden.uproject` makes the Launcher/editor pick the installed 5.8 engine.
- `unreal/Lunden/ENGINE_VERSION` holds the exact hotfix (`5.8.4`). `check-environment.ps1` (and every script that runs the
  engine) reads `Engine\Build\Build.version` and fails with exit code 3 on any other version:
  `ERROR: Wrong engine version: found 5.8.3 …, the project is locked to 5.8.4`.
- Upgrading (a new 5.8 hotfix, or 5.9 once it is stable) is a deliberate change in its own issue: update
  `ENGINE_VERSION` (and `EngineAssociation` for a minor version), rebuild, re-run the tests.

## No windows on the user's desktop (user, 2026-11-21)

Agents run everything hidden; the user works on the same PC. Never open a visible window:

- Unreal (editor commandlets, packaged game, tests): `-unattended -nosplash` plus `-RenderOffScreen` when frames are
  needed (screenshots, rendering tests) or `-nullrhi` when they are not. Never start the editor GUI or a game window.
- Windows Git: `git.exe -c core.editor=true` with `-m`/`-F` (an editor once opened on the desktop).
- PowerShell/other Windows tools from WSL: run as console processes (`powershell.exe -NoProfile -File …`); a tool that
  would open a window gets its headless flag or is started hidden (`Start-Process -WindowStyle Hidden`).

If a check genuinely needs a visible window, ask the user first.

## Where the Unreal checkout lives

The global WSL rule is to work in ext4 mirrors, but the Unreal editor, UnrealBuildTool and Visual Studio are
Windows programs: building a project on a `\\wsl.localhost\…` path is slow or fails. **Decision (#2243, can be
overturned in one sentence): Unreal work runs in a dedicated Windows clone,
`C:\Users\Olof\Documents\lunden-unreal-engine`**, made and committed with **Windows Git** (Git LFS 3.8.1). It is a
plain clone of GitHub, **not** the `winc` side of the WSL mirror (`C:\Users\Olof\Documents\lunden-3d-apartment`)
and **not** registered with `wsl-repo-sync`: the mirror must stay clean for the sync (see below), and engine output
(`Binaries/`, `Intermediate/`, `Saved/`, `DerivedDataCache/`) would otherwise sit in the synced tree. One-time setup:

```text
git clone --filter=blob:none https://github.com/solwation/lunden-3d-apartment C:\Users\Olof\Documents\lunden-unreal-engine
cd C:\Users\Olof\Documents\lunden-unreal-engine
git lfs install --local
git config lfs.fetchexclude ""
git lfs pull
```

The scripts refuse to run the engine on a WSL/UNC checkout (exit code 6) and only warn in `check-environment.ps1`.
For the first content-only cook, use a fresh Windows checkout. Earlier native or temporary
build targets in an old checkout’s ignored `Intermediate/` or `Binaries/` can make UAT
look for a project-specific editor receipt.

- WSL Git has **no git-lfs**. A `.uasset` committed from WSL would bypass the LFS filter and land in normal Git
  history. Commit Unreal binaries only with Windows Git (`"/mnt/c/Program Files/Git/cmd/git.exe"` from WSL, or
  Git for Windows directly) until git-lfs is installed in WSL.
- Text files (`.uproject`, `Config/`, `Content/Python/`, `tools/unreal-engine/`, this document) can be edited and committed
  from the ext4 mirror as usual; the LFS rules do not touch them.
- **LFS and the WSL mirror (verified 2026-11-20 with throwaway clones):** WSL Git without git-lfs checks out an LFS
  commit as the 129-byte pointer text and `git status` stays clean (`git hash-object` of the pointer equals the
  committed blob). A WSL push to an `updateInstead` mirror on `/mnt/c` writes the pointer too, and Windows Git in
  that mirror also reports it clean; a Windows Git checkout there keeps the pointer (`.lfsconfig` excludes
  `unreal/**`) and marks the `lockable` file read-only, which a later WSL push still replaces. **The one way to break
  the sync:** real LFS content in the mirror (someone runs `git lfs pull` or clears `lfs.fetchexclude` in
  `C:\Users\Olof\Documents\lunden-3d-apartment`). Both Gits then report the `.uasset` as modified, `updateInstead`
  rejects every push ("Working directory has unstaged changes") and `wsl-repo-sync` stops with a warning. Never
  pull LFS content into the mirror; Unreal work belongs in the dedicated clone.

## Scripts (`tools/unreal-engine/`)

All scripts are PowerShell (Windows PowerShell 5.1 or PowerShell 7), run on Windows and callable from WSL:

```text
powershell.exe -NoProfile -File tools/unreal-engine/check-environment.ps1
powershell.exe -NoProfile -File tools/unreal-engine/build-editor.ps1 [-Configuration Development|DebugGame]
powershell.exe -NoProfile -File tools/unreal-engine/run-python.ps1 tools/unreal-engine/python/smoke_create_asset.py [args…]
powershell.exe -NoProfile -File tools/unreal-engine/run-tests.ps1 [-Filter Editor.Python.Lunden.] [-WithRhi]
```

Run repository scripts on a Windows host whose existing policy permits them. Every engine script
takes `-EngineDir <root>` (or the environment variable `LUNDEN_UNREAL_ENGINE_ROOT`); otherwise the engine is found through the
registry (`HKLM\SOFTWARE\EpicGames\Unreal Engine\5.8`), the Launcher's `LauncherInstalled.dat` and finally the
default path. Logs go to `unreal/Lunden/Saved/Logs/<script>-<time>.log` and test reports to
`unreal/Lunden/Saved/Automation/<time>/` (both ignored by Git).

| Script | Runs | Success means |
|---|---|---|
| `check-environment.ps1` | nothing; reports project, engine, VS/MSVC, SDK, .NET | exit 0 and `OK: …` |
| `build-editor.ps1` | reports the content-only project status | exit 0 |
| `run-python.ps1` | `UnrealEditor-Cmd.exe <uproject> -run=pythonscript -script="<file> <args>" -unattended -nullrhi …` | exit 0 **and** no `LogPython: Error`/traceback in the log |
| `run-tests.ps1` | `UnrealEditor-Cmd.exe <uproject> -ExecCmds="Automation RunTests <filter>; Quit" -TestExit="Automation Test Queue Empty" -ReportExportPath=… -nullrhi` | editor exit 0 and report `index.json` with ≥ 1 passed, 0 failed and 0 not run |

Exit codes (all scripts): 0 ok, 1 command failed, 2 engine not found, 3 wrong engine version, 4 toolchain
(VS/MSVC/SDK/.NET targeting pack) missing, 5 project files invalid, 6 checkout on a WSL/UNC path.
When the environment is not usable the scripts run **nothing**: they print the problems and the exact command they
would have run.

Verified engine behaviour (5.8.4): `UnrealEditor-Cmd` returns non-zero whenever the log's final *Warning/Error
Summary* contains an error (exit 1, e.g. two Asset Manager errors before the GameFeatureData rule existed), −1 when
a Python script raises or cannot be loaded, and 255 when an Automation Test fails. `run-python.ps1` passes the script
path with forward slashes, because with arguments the commandlet parses `-script` as a command line in which a
backslash is an escape (`\tools` became `<TAB>ools`); paths with spaces are not supported in that form.
`index.json` from the Automation report has the fields `succeeded`, `succeededWithWarnings`, `failed` and `notRun`.
`run-tests.ps1` activates Epic's prebuilt `PythonAutomationTest` editor plugin and selects
`Editor.Python.Lunden.` by default. The fixture test loads the versioned LFS material
through the editor. `run-python.ps1` and `run-tests.ps1` check the engine lock without
requiring a C++ compiler. Use `check-environment.ps1 -SkipToolchain` for the same
editor-only check. The scripts that start the editor store their logs and reports under `unreal/Lunden/Saved`. The smoke script creates and
removes its own ignored `/Game/Lunden/_Smoke` folder. In the #2268 isolated content-only
check on UE 5.8.4, the Epic-signed editor returned 0 and `LUNDEN_SMOKE_OK`.
Automation reported one pass for `Editor.Python.Lunden.test_fixture_material`.
With the material removed from that copy, the same test reported one failure
and exit 255. The check produced no project DLL and no new Code Integrity
3033/3077 events for Lunden DLLs. These command lines ran directly through
the installed editor on the Smart App Control host.

For local Shipping archives, see [Build location](#build-location-decision-2244).

## Git LFS (Unreal only)

`.gitattributes` in the repository root puts **only files under `unreal/`** in Git LFS:

- `unreal/**/*.uasset` and `unreal/**/*.umap`: `filter=lfs diff=lfs merge=lfs -text lockable`;
- source art and import files under `unreal/`: `*.fbx *.obj *.glb *.exr *.hdr *.png *.tga *.psd *.tif *.tiff
  *.jpg *.jpeg *.wav *.ogg *.mp3 *.mp4` (LFS, not lockable).

**Never add an LFS rule outside `unreal/`.** GitHub Pages cannot serve LFS files and the Pages checkout does not
fetch them, so an LFS-tracked web file (`models/*.glb`, `music/*`, `textures/*`, `data/*`, `icons/*` …) would be
published as its pointer text ([GitHub: Git LFS and Pages](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-git-large-file-storage)).
Check with `git check-attr -a -- <path>`: web paths must print nothing, `unreal/**/*.uasset` must show `filter: lfs`
and `lockable: set`.

`.lfsconfig` sets `lfs.fetchexclude = unreal/**`, so agent clones, cloud sessions and CI never download Unreal
content. The Unreal checkout opts in locally, once:

```text
git config lfs.fetchexclude ""
git lfs pull
```

**Quota (user decision, non-blocking now; #2242 point 3):** GitHub Free includes 10 GiB LFS storage and 10 GiB
download per month ([billing](https://docs.github.com/en/billing/concepts/product-billing/git-lfs)). Every saved
version of a binary `.uasset` is stored in full, and every clone that pulls LFS downloads it. Recommendation: start
on Free, report the LFS size in each Unreal delivery (`git lfs ls-files -s`), add large source files (raw EXR,
photos) only when they are actually used, and keep generated imports (#2245) out of Git where possible.

## Web protection

- `.github/workflows/pages.yml` ignores pushes that only change `unreal/**`, `tools/unreal-engine/**` or `shared/schema/**`
  (the JSON schemas planned in #2245, not loaded by the web), in addition to docs/material/cloudflare/`*.md`.
  A web change still deploys as before.
- `tools/stamp.sh` copies an explicit list of web files (unchanged) and, at the end, **fails the build** with
  `::error::` if any published file starts with `version https://git-lfs.github.com/spec/v1` or has the extension
  `.uasset/.umap/.pak/.utoc/.ucas`. A clean build prints `site ok: no Git LFS pointers or Unreal packages in …`.
- Unreal changes need **no** `data/changelog.json` entry: that file is the web version's note on the freezer. The
  Unreal version's change history becomes release notes (#2250).

## Claude Code and MCP

Stable automation does not depend on MCP: headless Python (`run-python.ps1`), commandlets, Automation Tests
(`run-tests.ps1`) and later `RunUAT BuildCookRun` are the primary route. MCP is a complement for interactive work in
an open editor.

- **Plugins in `Lunden.uproject`:** `ModelContextProtocol` (the server, "Unreal MCP", experimental in UE 5.8) and
  `AllToolsets` (mounts the toolset plugins; without it the server exposes no tools). Both exist in 5.8.4 under
  `Engine/Plugins/Experimental/` (verified). Names first came from Epic's
  [setup.md](https://github.com/EpicGames/unreal-engine-skills-for-claude-code-plugin/blob/main/skills/unreal-mcp/references/setup.md).
- **Claude Code plugin** (Epic, MIT): https://github.com/EpicGames/unreal-engine-skills-for-claude-code-plugin.
  Optional: `/plugin install unreal-engine-skills-for-claude-code@claude-plugins-official`. It ships skills
  (`unreal-mcp`, `unreal-skill`, `create-toolset`) and a SessionStart hook that needs `bash`; no MCP server of its
  own. Not installed by #2243.
- **Start the server** per session: editor console `ModelContextProtocol.StartServer [port]` (stop:
  `ModelContextProtocol.StopServer`), or start the editor with `-ModelContextProtocolStartServer`
  (`-ModelContextProtocolPort=N` to change the port). Auto-start is per user only
  (`Saved/Config/WindowsEditor/EditorPerProjectUserSettings.ini`, `[/Script/ModelContextProtocolEngine.ModelContextProtocolSettings]`
  `bAutoStartServer=True`) and deliberately not in the shared `DefaultEditor.ini`; commandlets never auto-start it.
- **Verified 2026-11-20:** the editor logs `Created new HttpListener on 127.0.0.1:8000`; the listener binds loopback
  because `[HTTPServer.Listeners] DefaultBindAddress` defaults to `localhost` (leave it unset; `any` would expose it).
  `initialize` → protocol `2025-06-18`; `tools/list` returns the three meta-tools `list_toolsets`, `describe_toolset`
  and `call_tool` (tool search), and `list_toolsets` lists the toolsets (Automation tests, config settings, editor,
  logs, …). The [forum report](https://forums.unrealengine.com/t/5-8-experimental-modelcontextprotocol-mcp-server-instantly-drops-connections/2729488)
  of 5.8 dropping connections did not reproduce over plain HTTP requests.
- **From WSL:** this PC runs WSL2 in **NAT** networking (`wslinfo --networking-mode` = `nat`). A WSL process cannot
  reach Windows loopback (`curl http://127.0.0.1:8000/mcp` → connection refused; the host IP times out because the
  server is not bound there). Mirrored networking or a wider bind would change Windows/WSL settings or expose the
  port, so instead `tools/unreal-engine/mcp-bridge.py` is a stdio MCP server for Claude Code that forwards each
  JSON-RPC message with the Windows `curl.exe` (WSL interop) to `127.0.0.1:8000`; the server stays loopback-only.
  Verified from WSL: `initialize`, `tools/list` and `describe_toolset` through the bridge. Register it **locally**
  (machine config, never committed), from the ext4 checkout:

  ```text
  claude mcp add --scope local unreal-editor -- python3 /mnt/c/Users/Olof/Documents/lunden-unreal-engine/tools/unreal-engine/mcp-bridge.py
  ```

  Claude Code running on Windows can instead connect directly: `claude mcp add --transport http unreal-editor
  http://127.0.0.1:8000/mcp`. Check with `/mcp` and a read-only `list_toolsets`. Limits of the bridge: one request
  at a time, no server-initiated stream. Without a running editor every call returns a clear error.
- **Security boundary:** the server has **no authentication**; any process of the same Windows user (and, through
  the bridge, of the WSL user) can call it. `ProgrammaticToolset.execute_tool_script` runs arbitrary Python in the
  editor. Do not run the MCP server on a shared machine, never expose the port, commit before long MCP sessions and
  review the diff. Stop the server (or the editor) when done.

## Parallel work: levels and Blueprints

Binary Unreal assets (`.umap`, `.uasset`) cannot be merged. These rules let the porting issues (#2247; the
[issue table](unreal-inventory.md#porting-issues-release-1) names each one's write area) run at the same time.
They apply together with the [hidden-window rule](#no-windows-on-the-users-desktop-user-2026-11-21): every step
below runs headless.

**Ownership.**

- **One owner per binary asset, level and content folder at a time**, named in the owning issue's "Ägarskap"
  section. An issue writes only the `/Game/Lunden/<Area>/` folders, levels and builder scripts it names. It reads
  other areas' assets and references them by path or actor tag, never by editing them. Ownership passes only by
  explicit handover in both issues (for example from the pilot #2246 to the issue that takes over its assets).
- **One owner per zone level.** The world is a persistent map, `/Game/Lunden/Maps/L_Lunden`, with one sub-level per
  zone and area. The issue that owns the persistent map rebuilds it with its composition script from a text list of
  sub-levels. Other issues add their own line to that list and never open the persistent map. Each sub-level
  has exactly one owning issue. Generated zone levels (`/Game/Lunden/Generated/<zone>/Level_<zone>`) stay owned by
  the importer, and an area that needs to change imported actors makes a derived sub-level through its own builder
  under `Generated/<Area>/`, as the pilot's door builder does.
- **One file per actor (OFPA) is optional, not the default.** The importer writes plain levels, and plain
  sub-levels per zone are what the pilot verified. A hand-made sub-level that several issues will fill over time may
  turn on external actors (`__ExternalActors__/`, one `.uasset` per actor) so that owners of different actors do not
  collide. Its level file still has one owner. World Partition is not used, because a World Partition map cannot
  hold streamed sub-levels. Decide again in its own issue if the outdoor world outgrows sub-levels.
- **Seams instead of shared assets.** When another area must hook into an owned class (GameMode, PlayerController,
  character, HUD, avatar, door), the owner exposes an extension point that is read from text. Examples are a JSON
  list of component classes that its builder adds or Blueprint event dispatchers that others bind to at run time.
  The other issue changes only that text or binds from its own assets.

**Locking (Windows Git in the dedicated Unreal clone).**

1. Check `git lfs locks` and the owning issue before touching a binary. Someone else's lock means stop; never use
   `git lfs unlock --force` on another owner's lock without a handover recorded in both issues.
2. `git lfs lock <path>` for every `.umap`/`.uasset` you will write, including assets a builder regenerates. With
   `lockable`, an unlocked file is checked out read-only, so a builder that forgot the lock fails early.
3. Commit and push, then `git lfs unlock <path>`. Do not keep a lock across a pause or a handover. Release it, or
   hand it over explicitly.
4. Text files (`tools/unreal-engine/**`, `Config/*.ini`, `Lunden.uproject`, `shared/`, `cloudflare/`, docs) are not
   locked. Several issues may change them by ordinary rebase. Each issue lists the shared text files it touches and
   keeps its change additive.

**Blueprint/Python split in the content-only project (#2268).** The project has no C++ module and no plugin with
its own binaries, so the editor and the packaged game load only Epic-signed code.

- **Runtime logic is Blueprint**, using engine classes, components and Epic-shipped plugins that are enabled in
  `Lunden.uproject`. Keep each Blueprint small and owned by one area: components and function libraries rather than
  one large actor.
- **Editor Python is the source of every hand-maintained asset.** Each area has a builder,
  `tools/unreal-engine/python/build_<area>.py`, that creates or updates its Blueprints, graphs, input assets,
  materials and sub-levels headless (as `build_player.py` and `build_pilot_doors.py` do). The committed `.uasset`
  is the builder's output: review the script diff, regenerate with the lock, commit both. Agents never edit
  assets in the editor GUI.
- **Python never ships.** The packaged game runs Blueprints and assets only. Editor Python covers import, builders
  and tests (`tools/unreal-engine/tests/test_<area>.py`, run through `PythonAutomationTest` in Play In Editor).
- **Shared values come from data.** Read measurements, IDs and rules from the #2245 export (`measurements.json`,
  actor tags) or from DataTables and DataAssets that a builder fills from it. Do not hand-copy web numbers into
  graphs.
- **A missing engine capability is a decision, not a workaround.** If a feature needs something no Epic-shipped
  plugin exposes to Blueprint, such as a general WebSocket client, stop and ask the user on the issue
  (`user-question`). Adding native code reopens #2268.
- `Content/Lunden/Generated/` is written only by scripts: the #2245 importer and the derived-level builders, each in
  its own `Generated/<folder>/`. Hand edits there are lost on the next run.
- Different tools folders can be worked on in parallel (`tools/unreal-engine/export*`, `tools/unreal-engine/package*`,
  `unreal/Launcher/`; #2242).

## Player (#2284)

`/Game/Lunden/Player/` holds the production first-person player; #2284 owns the folder, `build_player.py`,
`tests/test_player.py` and the format of `player-extensions.json`. It took over the #2246 pilot's assets with their

`IA_Lunden*` actions → `Input/`. `Blueprints/Pilot/` is empty; `Blueprints/PilotDoors/` keeps only `BP_LundenSwingDoor`
(the door area, #2285). `L_Lunden` and `Pilot_L1007` use `BP_LundenGameMode`.

```text

powershell.exe -NoProfile -ExecutionPolicy Bypass -File tools/unreal-engine/run-python.ps1 tools/unreal-engine/python/build_player.py [<measurements.json>] [--force | --check] [--extensions <file>]
```

**Values come from the export.** `measurements.json` `spawn.player` (`src/config.js` `PLAYER`) and `spawn.fall`
(`FALL`, `COMBAT.lives` and sample results of the web's own `src/falldamage.js`, added to `export-scene.js` by #2284).
The builder writes them into the character's movement settings and Blueprint variable defaults (`WalkSpeed`,
`RunSpeed`, `LookDegrees`, `MaxLives`, `Lives`, `FallHurt`, `FallFatal`, `FallMaxReport` in cm); the graphs read
the variables, never a literal web number. Capsule radius 22 cm, half height 92.5 cm (headroom 1.85 m / 2), step
45 cm, jump 370 cm/s (apex 69.8 cm with Unreal's default gravity of 980 cm/s², the web's 9.8 m/s²), walk 160, sprint
320, crouched 80 cm/s (`walk × crouchSpeed`). Eye heights: standing 162, crouched 95 cm above the floor; the eye
offsets subtract the 2.15 cm the walking capsule floats above the floor. *Assumption:* the crouched capsule keeps the
standing headroom over the eye (half height 59 cm); the web has no crouched body height. Not yet ported: the faster
outdoor sprint `runOutdoor` (needs an indoor/outdoor signal), rest (`src/rest.js`) and the footstep surface sensor
(`src/stepsurface.js`).

**Mouse look (#2294).** `src/main.js` turns the view by `PLAYER.mouseSens` (0.0013 rad, 0.0745°) per pixel of mouse
movement, up looks up. The graph multiplies the raw MouseX / MouseY counts by `LookDegrees` (that value in degrees)
into `AddControllerYaw/PitchInput`. Two engine settings from the 5.8 template are switched off in
`Config/DefaultInput.ini`, and `build_player.py` refuses to build or pass `--check` when either is back:
`bEnableLegacyInputScales=False` (with it on, `BaseGame.ini` `InputPitchScale=-2.5` inverted the pitch and
`InputYawScale=2.5` multiplied the yaw) and `Sensitivity=1` on the MouseX / MouseY `AxisConfig` (the template's 0.07
reached the look actions too). The pilot therefore turned at 0.175 times the web's rate with the pitch inverted; now
one count is 0.0745° on both axes. Not yet ported: the web's pitch limit of ±1.45 rad (Unreal keeps its default
±89.9°) and an inverted-Y setting.

**Fall damage** (`src/player.js` landing, `src/falldamage.js`, `src/combat.js` `fall`). A fall starts when the
character enters Falling (take-off of a jump, or the ledge it walked off) and its drop is that capsule height minus
the landing height. Unreal only falls in free drops, since stairs and steps up to 45 cm stay in Walking, so the web's
gap under the feet is never smaller than the drop. The rule is therefore: drop over `FallMaxReport` (100 m) costs
nothing (the web reports no damage), over `FallFatal` (6 m) costs `MaxLives`, over `FallHurt` (3 m) costs
ceil(`MaxLives` / 2), else nothing. Lives drop by the damage, and a death (damage ≥ lives) refills them and counts
`Deaths`; `LastFallDrop` and `LastFallDamage` hold the latest landing for #2293's shared life and the HUD. The
blackout, outdoor wake and suit protection stay with #2293/G08. Floor checks use a flat base
(`use_flat_base_for_floor_checks`): with the round capsule bottom the character sank up to 17 cm down a ledge before
falling, and the drop came out short.

**Extension point.** `tools/unreal-engine/player-extensions.json` (`formatVersion` 1) lists components as
`{target: character | controller, name, class, owner, what}`. `build_player.py` adds each missing row's component to
`BP_LundenPlayer` or `BP_LundenPlayerController`. It removes components it added earlier whose row is gone, recorded
in the asset metadata `Lunden.PlayerExtensions`, and leaves every other component alone. #2285, #2286, #2287, #2288
and #2292 add their rows here and never open the player Blueprints.

**Idempotency.** The builder stores a hash of its inputs (export values, extension rows, the script itself) as
`Lunden.SpecHash` on `BP_LundenPlayer`; a run with the same inputs logs `unchanged, nothing saved`. `--check` fails
when the assets are missing, the hash differs or a pilot asset is still in its old folder. A changed input rebuilds
the character's event graph from scratch and rewrites the defaults.

## Save file (#2288)

The web keeps the player's name (`lunden.name`), opaque id (`lunden.playerId`, a `crypto.randomUUID()`), look code
(`lunden.avatar`), settings and place (`src/resume.js`, `lunden.playerWorld`) in browser storage
([storage](storage.md#local-player-profiles-1515)). The Windows game keeps them in one versioned SaveGame slot,
`LundenSave`, written by the engine to `<user dir>\Saved\SaveGames\LundenSave.sav`. The launcher starts the game
with `-UserDir=%LOCALAPPDATA%\Lunden` (`Lunden-Test` for the test channel), so the file lives outside the
installation, is never part of a version tree and is kept by a default uninstall ([launcher](#windows-launcher-2249)).
In the editor it is `unreal/Lunden/Saved/SaveGames/LundenSave.sav`. #2288 owns `/Game/Lunden/Save/`, `build_save.py`,
`tests/test_save.py`, `tests/save-v0.sav` and the `Save` row of `player-extensions.json`.

- **`SG_LundenSave`** (SaveGame): `SaveVersion`, `PlayerName`, `PlayerId`, `LookCode`, `PlaceMap`, `PlaceLocation`
  (cm), `PlaceRotation` (the control rotation: pitch and yaw) and `Settings` (string → string).
- **`BFL_LundenSave`** (function library) is the interface for other areas: #2286 uses `GetSetting(Key, Default) →
  Value, Found` and `SetSetting(Key, Value)`, #2291 `GetLookCode`/`SetLookCode`, #2292 `GetPlayerName`/`SetPlayerName`
  and `GetPlayerId`. Every call reads the slot and every setter writes it back at once, so callers keep no copy and
  never overwrite each other. `LoadSave()` always returns a save: a missing or unreadable slot becomes a new save with
  a new id, written at once. Settings are strings under keys the owning area chooses (for example
  `mouse.sensitivity`); convert numbers with the string conversion nodes. `NewPlayerId()` makes a lower-case
  8-4-4-4-12 id like the web's.
- **`BPC_LundenSave`** rides on `BP_LundenPlayerController` (`player-extensions.json` row `Save`). At BeginPlay it puts
  the possessed pawn back at the saved place and facing when the save was made on the same map (`K2_TeleportTo`, which
  refuses or nudges a spot that something now blocks; the body takes the yaw, the view pitch and yaw), retrying every
  `RetrySeconds` until a pawn is possessed. Then it saves the place every `SaveIntervalSeconds` (2 s, like the web's F5
  record) and at EndPlay. A save from another map (the pilot map, a test level) is not applied.
- **Versions and migration.** `SaveVersion` defaults to 0 on the class and a SaveGame stores only properties that
  differ from the defaults, so a file written before the field existed reads as 0. New saves get `CurrentVersion()`
  (1). `MigrateSave` brings an older save up one step at a time and `LoadSave` writes the result back; 0 → 1 adds the
  player id. A new version adds a step there, keeps old field names and types (a renamed field reads as empty) and a
  frozen file of the old layout under `tests/`, as `save-v0.sav` is for version 0. A save from a newer build (after a
  launcher rollback) is read as far as this build knows it; fields it does not know are dropped at its next write.
- **Not in the save:** the home and life simulation (G13, later), cloud storage, several local profiles (the web's
  `lunden.players.v1`; one player per Windows user for now) and the web's two-minute "Ladda om" record (the game
  always resumes at the last place).

## Build location (decision #2244)

**Decision (agent's recommendation, alternative 1; can be overturned in one sentence):** Unreal is built **locally
with scripts on the Windows development PC**; signing and publishing happen later in **GitHub Actions** (#2250).

- Why: GitHub-hosted Windows runners have 14 GB SSD — too little for the engine, project and Derived Data Cache.
  The repository is public, and a self-hosted runner on a public repository can be made to run code from other
  people's pull requests (booster-ai avoids it for the same reason). A cloud GPU VM costs money per hour and is not
  justified now.
- Security boundary: keep all signing keys and Azure credentials off the build PC. The local step retains the vendor signatures in the archive. A separate handoff to a draft release or artifact and signing/publication belong to #2248/#2250.
- Derived Data Cache: use the local Zen DDC on a fast disk outside the checkout. The default on Windows is
  `%LOCALAPPDATA%\UnrealEngine\Common\Zen\Data`. Set `UE-ZenDataPath` for a different local disk.
  [Epic documents the Zen data location and overrides](https://dev.epicgames.com/documentation/en-us/unreal-engine/using-zen-storage-server-as-cooked-output-store-for-unreal-engine).
- Another Windows PC can take over by following the install steps above, cloning the repository, running
  `git config lfs.fetchexclude ""` + `git lfs pull` and `check-environment.ps1`.

### Building a local Shipping archive

Use Windows Git to check out the intended commit with all Unreal LFS objects. Verify
`check-environment.ps1` on that checkout. From Windows PowerShell run

```powershell
.\tools\unreal-engine\release.ps1 -Version 0.1.0 -Content 12 -OutputRoot D:\LundenBuilds
```

`-Version` is the app version and `-Content` is its accompanying content version
(nonnegative integer). The default output root is `%LOCALAPPDATA%\Lunden\Builds`.
The script checks for staged, modified and untracked files before calling
`RunUAT.bat BuildCookRun` for a Win64 Shipping cook, stage, IoStore package and
archive. It uses the installed target with `-nocompileuat -nocompile -skipbuild`
and omits the locally customized bootstrap with `-nobootstrapexe`. The MCP and
toolset plugins are enabled for Editor, and AndroidFileServer stays disabled in
Editor. Shipping uses the plugins compiled into Epic's stock UnrealGame.
Changing the runtime plugin set makes UAT generate a temporary native target.
The script checks HEAD and worktree cleanliness again after UAT. Each invocation
creates a separate directory under the output root containing `BuildCookRun.log`
and `archive/Windows/`. All invocations stage at the one fixed path
`<OutputRoot>\stage`, which the script empties before UAT; a named mutex lets only
one release build per PC run at a time (see [Pak repeatability](#pak-repeatability-2248)).
UAT can also use the engine's ordinary ignored
intermediate files in the project.

A completed archive contains the Shipping executable and `build-info.json` beside
the packaged `Lunden/` folder. The metadata contains `appVersion`, `contentVersion`,
the full Git `commit`, the actual `engineVersion`, the committed script blob ID
(`releaseScriptBlob`), completion time in UTC (`builtUtc`) and the verified
`runtime.path`, `runtime.sha256` and `runtime.publisher`. The archived
`Engine/Binaries/Win64/UnrealGame-Win64-Shipping.exe` must match the SHA-256
of the installed runtime and have a valid Epic Games Inc. Authenticode signature. A failed build
can leave files and its log in its own build directory. Hand off only a completed
archive. For #2248, build twice from one commit and compare the resulting program
and container files across the two archives.

#### Pak repeatability (#2248)

UnrealPak seeds the pak index's path-hash table with `FCrc::StrCrc32` of the lowercase
**full output `.pak` path** (`FPakFile::EncodePakEntriesIntoIndex` in
`Engine/Source/Runtime/PakFile/Private/PakFile.cpp`). It stores that seed in the primary index, so the
runtime reads any value. Before the fix, `release.ps1` staged every build in its own GUID directory. The two
#2244 paks from `c70a0bd2` had the same entry list, offsets, sizes, SHA-1 values and data in
`UnrealPak -List`. Only three byte ranges after the last entry differed: the seed and the path-hash index hash in the
primary index, 20,756 bytes of the path-hash index (1,730 × 12-byte hash entries) and the footer's index hash.
The stored seeds `0xe6fc0ff4` and `0x15851533` equal the CRC-32 of each run's staged pak path.

`release.ps1` now stages at `<OutputRoot>\stage` for every build. Two runs of commit `74dd7a82` in a fresh
Windows worktree (exit 0, 75 s and 33 s) gave the same `Lunden-Windows.pak` SHA-256
`bf2fdbc5e700fd2b9a4aacd7c8eefe7d441abf4408d439622859988865d0af8d` (11,226,745 bytes); all five containers
and 23 of the 26 archived files were identical. Only `build-info.json` and UAT's two `Manifest_*UFSFiles_Win64.txt`
differed, and `make-manifest.mjs` ignores all three. Keep the same `-OutputRoot` (the default
`%LOCALAPPDATA%\Lunden\Builds`) for successive releases. A different root changes the seed and re-sends the
roughly 11 MB chunk-0 pak, even when its content is unchanged.

Run `node tools/unreal-engine/compare-cooks.mjs FIRST_PAKS SECOND_PAKS` against each
archive's `Lunden/Content/Paks` directory. It streams each container and reports its
relative name, size and SHA-256. [Full five-file comparison](../verification/2248/stock-cooks.json).

With two independently assigned zones in a fixed project directory, the two clean baseline
cooks matched byte for byte across all 11 containers. Moving one actor in Zone A changed
its chunk 1 UCAS and UTOC and chunk 0's PAK (the embedded `AssetRegistry.bin` changed).
The other eight containers, including Zone B's entire chunk, remained identical. A client
running the original signed stock executable displayed the moved actor after replacing

#### Sign a release manifest in Actions

The manifest key is an ECDSA P-256 pair (decision on #2248, 2026-11-20). The private key
was never written to disk. It exists only as the secret `LUNDEN_MANIFEST_PRIVATE_KEY` in
the protected `signing` environment, so it never reaches the build PC (#2244). The public

promotion verifies against it. A repository admin creates the pair once with
`tools/unreal-engine/create-manifest-key.sh`, which generates the key with `openssl` in shell memory and
pipes it straight into `gh secret set … --env signing`. Only the public key goes to `gh variable set`.
The script refuses if either value already exists. `--dry-run` checks access and
prints a throwaway public key without storing anything.

Upload `lunden-manifest-test.json` (or `lunden-manifest.json`) from `make-manifest.mjs` to the
versioned release, either as a draft or published without **Set as latest release**. Then run
**Sign an Unreal release manifest** ([workflow](../../.github/workflows/sign-manifest.yml)).
The `signing` environment only deploys from tags matching `v*`. A `workflow_dispatch` run
deploys from the ref it was started on, so the run must start from a `vMAJOR.MINOR.PATCH`
launcher tag whose commit contains the workflow. The release to sign is an input:

```sh
gh workflow run sign-manifest.yml --ref v0.2.1 -f tag=content-13 -f asset=lunden-manifest-test.json
```

The tag, release and asset names above are examples. Starting from a branch fails in the
unprivileged preflight job, before the environment is requested. Only tagged code ever sees
the key. The protected job has three steps:

1. `sign-manifest.mjs fetch`, with a token and no key, finds the single release with that tag
   (drafts included). It refuses the current latest release or an existing `.sig`, and
   downloads the manifest after checking its size and GitHub digest.
2. `sign-manifest.mjs sign`, with the key and no token, makes no network requests. It checks that
   the private key matches the public variable and signs the exact bytes as a 64-byte P1363
   signature. It keeps the signature only if the [verifier](../../tools/unreal-engine/verify-published.mjs)
   accepts it with the public key, schema and channel rules.
3. `sign-manifest.mjs upload`, with a token and no key, rechecks the release ID and the
   manifest asset (ID, size, digest and update time), verifies again and uploads
   `<asset>.sig`. It then downloads the uploaded asset and compares the bytes.

The workflow never changes latest. Promotion is still a separate step. The workflow
shares the promotion gate's concurrency group. To sign again, first delete the old `.sig`
asset deliberately. If the repository enables immutable releases, sign before publishing
the draft. Tests: `node --test tools/unreal-engine/tests/sign-manifest.test.mjs` (simulated
release API, throwaway in-memory keys) and `tools/unreal-engine/tests/create-manifest-key.test.mjs`
(fake `gh` on `PATH`; the private key reaches only its stdin). The Windows launcher test
workflow also runs `NodeSignedManifestTests`, so a Node-produced `.sig` must pass the C# reader.

**Rotation needs a launcher update.** Each launcher embeds the public key at build time and
accepts only manifests signed by that key, including the manifest that offers a launcher
self-update. `create-manifest-key.sh --rotate` replaces the secret and the variable together. The
old private key is gone, and promotion and the next launcher build immediately use the new
public key. Installed launchers then reject every new manifest. They must be reinstalled from a
new installer that embeds the new key. A transition without reinstalling would need one
last old-key manifest that delivers a launcher with the new key. The current tooling does
not support that, because it holds only one key. Treat a leaked private key as compromising
every installed launcher until users have replaced it.

### Publisher identity (#2277)

Azure Artifact Signing issues a new **leaf certificate every 72 hours**, and Microsoft rotates the
issuing CA as well. Pinning a leaf (the earlier `LUNDEN_SIGNER_SHA256`) would make every release
signed after the next rotation fail its own packaging check, and installed launchers would reject
the next update. The launcher therefore trusts the stable identity in the reviewed
[`unreal/Launcher/publisher-identity.json`](../../unreal/Launcher/publisher-identity.json), compiled in
as an embedded resource like the Unreal inventory. A file from the project is accepted only when:

1. Windows `WinVerifyTrust` (Authenticode policy, revocation checked except for the root) returns success;
2. the verified signature carries a timestamp countersignature (RFC 3161), which keeps it valid after the leaf expires;
3. the leaf's subject has exactly one CN equal to `commonName` and exactly one O equal to `organization`;
4. the leaf has the code-signing usage `1.3.6.1.5.5.7.3.3` and the certificate profile's durable identity usage `identityKeyUsage`;
5. the chain Windows built ends at the self-signed root whose certificate SHA-256 is `rootSha256`.

Intermediates are not pinned: they changed between two signings nine days apart. No leaf is pinned;
the protected build record only documents which leaf signed (`signer.leafCertificateSha256`).
`SignerIdentity.cs` implements the check, `Authenticode.cs` reads the chain and timestamp from the same
successful `WinVerifyTrust` call. Reviewed vendor images (below) still pin their exact leaf, because
their bytes, and therefore their signatures, never change.

### Axes and units

Web/plan: metres, right-handed, x = east, y = up, z = south (north = −z) ([architecture](architecture.md#geometry-pipeline)).
Unreal: centimetres, left-handed, X forward, Y right, Z up. **Target mapping:** `Unreal X = 100·x`, `Unreal Y = 100·z`,
`Unreal Z = 100·y` (an axis swap, determinant −1: right-handed becomes left-handed without mirroring the plan; north is
Unreal −Y). Yaw: `unrealYaw = −90° − yawDeg` for `?at=`/`START` (web 0 north, 90 west, 180 south, −90 east, verified against
`src/player.js` `spawn`: `camera.rotation.y = yaw`, a camera looks down local −z); an object's `rotation.y` a
(radians) → `unrealYaw = 90° − a`; pitch unchanged. Implemented in `tools/unreal-engine/coordinates.mjs`;
`node tools/unreal-engine/coordinatestest.mjs` checks L1007's four outer corners (`data/plan.json`), the stair foot, START at eye
height and Övre plan's floor within 1 cm, a north arrow → Unreal −Y, and the yaw formula against the camera's real view

- **`export-manifest.json`**: `formatVersion`, source commit (+ dirty flag), SHA-256 per file, and every source file
  with its hash.

three.js is served from `node_modules/three` when it is the pinned 0.170.0 (else the CDN), the build and the
collection run synchronously before any later load, and nothing time-dependent is written. Two runs from the same
commit give byte-identical files. Size (2026-11-20): `l1007.glb` ≈ 81 MB, 2,614 nodes, ≈ 881k triangles (the

Run in the Windows clone after copying (or writing) the export to `unreal/Lunden/Import/`. Every run reads the

and checks it: ids, the fixture (zone `fixture`) and, with `--check`, the stamp and content fingerprint without

What 5.8.4 does, and what the importer does about it:

- **Scene import, not asset import.** `.glb` goes through Interchange's glTF translator either way. An
  `AssetImportTask` creates static meshes only, with node transforms **baked into the vertices** (every pivot at the
  world origin) and no actors. The importer uses `InterchangeManager.import_scene` with the project's default glTF
  scene stack (`DefaultGLTFSceneAssetsPipeline`, `DefaultGLTFPipeline`, `DefaultSceneLevelPipeline`) into a blank
  map: one actor per glTF node with its transform and attachment (a door's actor pivots at its hinge), StaticMeshes in
  local space under `<zone>/StaticMeshes/`, one MaterialInstanceConstant per material key under `<zone>/Materials/`
  and an `InterchangeSceneImportAsset`. The map is saved as `/Game/Lunden/Generated/<zone>/Level_<zone>` (a plain
  level, not World Partition: generated, one owner). Shared glTF meshes stay one shared asset.
- **Names and tags.** Interchange names actors `<zone>_node_<index>` and labels them with the node name; the importer
  renames each actor object to its id and keeps the id as label. Interchange stores node extras only as asset
  metadata on a StaticMesh (`INTERCHANGE.<node>.id` …, `EditorAssetLibrary.get_metadata_tag_values`), for the first
  node of a shared mesh, never on actors. The importer therefore reads the extras from the GLB and writes actor tags
  `[<id>, kind:<kind>, zone:<zone>, level:<n>, webId:<id>, source:<pointer>, parent:<id>]` (absent values left out).
  A node with `seasonal` extras and all its parts also get `seasonal`, `season:<what>`, `seasonFrom:<MMDD>` and
  `seasonTo:<MMDD>` (importer version 3; [Seasons](#seasons-2295)).
  Tags and object names survive packaging (labels are editor-only); Blueprints find objects with *Get All Actors
  With Tag* on the id.
- **Collision.** `collision` nodes (the web's wall rectangles and floor plates, one shared unit cube) get a single
  simple box on the cube mesh, `BlockAll`, hidden in game (54 in l1007). `StaticMeshEditorSubsystem` is `None` in the
  commandlet, so the deprecated `EditorStaticMeshLibrary` does it (a deprecation warning in the log). Visible meshes
  keep Interchange's default collision; what the player collides with is #2246.
- **Materials.** `tools/unreal-engine/material-map.json` rules (a regex on the key, first match wins, optionally
  narrowed by a `mesh` regex on the StaticMesh name) replace the imported instances on the mesh slots by hand-made
  materials ([Surface materials](#surface-materials-2282)). Other keys keep Interchange's glTF material instance
  (colour, roughness, metalness, opacity and emissive from the export).
- **Clearing a zone.** `EditorAssetLibrary.delete_directory` left the `.umap` behind, logged *Error opening file* for
  every package and was still working after 7 minutes on l1007's 2,426 assets (killed). `Generated/<zone>/` belongs to
  the importer alone, so it removes the folder on disk and rescans the asset registry when none of its packages is
  loaded (else the editor deletion). `LevelEditorSubsystem.new_level` saves an empty level at once and then refuses
  the path after a failed import, so the importer builds in a blank map and saves it with `save_map` at the end.

**Nanite materials in cooked builds (#2276).** The importer reads each mesh slot's
effective blend mode, including overrides on glTF instances. Any translucent or
otherwise unsupported slot sends that mesh through the regular raster path.
Opaque and masked Nanite meshes use a saved Nanite usage flag on project materials
and an explicit override on imported material instances. Interchange's engine
material stays shared. Importer version 2 regenerates older stamped zones.
After a fresh editor start, check the persisted settings without writing assets:

```powershell
.\tools\unreal-engine\run-python.ps1 tools/unreal-engine/python/prepare_nanite_materials.py --check l1007 l1007-uteplats
```

On the measured two-zone import, 1,896 meshes kept Nanite and 73 used raster
for unsupported blends. The clean read-back checked 461 apartment materials and
21 patio materials with zero changes, warnings or errors. The final runtime
check is a new Development cook and camera route with no missing Nanite usage or
default-material substitutions in the packaged process log.

**Idempotency, defined.** `Generated/<zone>/import-stamp.json` records the GLB's SHA-256 and source commit, the
importer version, the engine version, the hash of `material-map.json`, a content fingerprint and the SHA-256 of every
package file. When all of these match and every package file is byte-identical, the zone is **skipped and nothing is
written**; the check for "a second import changes no asset" is a byte comparison of every file under `Generated/`
before and after the run. A changed export, importer version, engine or material map, and any edited or missing
package file (a hand edit), re-imports the zone. A *forced* re-import (`--force`) is never byte-identical: every new
package gets a new persistent GUID (2,501 of 2,501 files differed). Its check is the **content fingerprint**, a SHA-256
over every actor (name, label, class, parent, transform to 0.01, tags, mesh, collision profile, hidden flag) and every
asset (class; for meshes vertices, triangles, bounds to 0.01, slot materials and simple boxes).

### Surface materials (#2282)

The export's keys describe a look (`std_<colour>_r<roughness>_m<metalness>` plus suffixes), not a surface, and its
canvas textures do not travel. `tools/unreal-engine/material-map.json` therefore holds three lists:

- `materials`: every hand-made asset in `/Game/Lunden/Materials/`. Three masters cover the building and ground
  surfaces: `M_LundenSurface` (plain opaque PBR), `M_LundenTiled` (tiles, slabs, planks, boards, bricks and fine
  aggregate drawn by one Custom HLSL node in the export's metre UVs) and `M_LundenGlass` (translucent glazing, so its
  meshes use the raster path, #2276). The `MI_Lunden*` instances take their sizes and colours from the web's
  `COLORS`, `FINISH`, `PATIO.paving` and `SCREEN_WALL`. `MI_LundenFacadeBrick`, `MI_LundenAsphalt` and
  `MI_LundenRoofSeam` are prepared for the exterior and ground zones (#2279, #2280) and no export key uses them yet.
  Each entry names its web `source` and an `assumption`; `build_materials.py` writes both into the asset metadata
  (`Lunden.Source`, `Lunden.Assumption`), so plan-material's *guess* markers stay with the material.
- `rules`: key → material. The tile key `std_ffffff_r100_m0_tex` is shared by the hall and wet-room floors, the wall
  tiles, the splashback, the patio paving and the screen walls, so its rules add a `mesh` selector (the StaticMesh
  name is the id of the first export node that uses it). The last rule for that key has no selector and catches any
  other surface with white wall tiles.
- `defaults`: keys left on Interchange's instance, each with a reason (plain opaque fittings, transparent and
  emissive fittings, textured fittings that belong to furnishing #2289, grass for #2281).

`scope` lists the zones and node kinds whose keys count as building and ground surfaces. Before an import, after the
export, run the coverage check (no Unreal needed):

```text
python3 tools/unreal-engine/tests/test_materials.py [<export dir>] [--table]
```

It fails when a key on those nodes has neither a rule nor a default, a rule names an unlisted material, a `mesh`
selector selects nothing (a moved surface changes its id), an instance names an unknown parameter, or an entry that
says *guess* has no assumption. `build_materials.py` skips an asset whose `Lunden.SpecHash` matches its entry, so a
second run writes nothing; `--force` rebuilds in place and `--check` verifies existence, spec hash, metadata,
parameters and the persisted Nanite usage without writing. Take `git lfs lock` on every `Materials/*.uasset` before a
build that writes. Results are in [the #2282 verification](../verification/2282/README.md).

**Terrain: the web's mesh, not a Landscape (decision #2280, can be overturned in one sentence).** The terrain is the

road bridge's asphalt, the timber bridge, the bus platform and world.js's level ground plates under Hus L and its
portik; 31 nodes) and writes `Generated/SiteWorld/Level_site_collision`: a complex-as-simple, double-sided copy of
each mesh with Nanite off (so neither #2298 nor #2299 applies), hidden in game on the imported actor's transform.
The water surface, kerbs, street furniture and parked cars get none. It replaced the provisional street ground of
`build_l1007.py` (#2278) and `build_exterior.py` (#2279). Hus L's and Hus A/B/C's façades still have no collision.

**Control points and route.** `groundProbes` in `export-scene.js` defines ten `elevation` points, on terrain-mesh
vertices where the web's terrain is `data/elevation.json` itself (src/surroundings.js `elevationWeight` 1), and seven
`terrain` points where the web departs from the elevation data by design: the courtyard (model y 0 on the garage box,
`SITE.terrain.ref`) and the carved Höje å valley (`SITE.river`). The exporter measures each on the exported walkable
nodes and writes `ground` into `measurements.json` with the elevation value, the web's `groundY` and drawn terrain.
`tests/test_site.py` (PIE on `L_Lunden`) traces the same points against the collision level (5 cm against the
elevation grid or the drawn terrain, and against the export's own hit on the same node), checks each collision copy's
bounds against its visible actor, and walks the route START → street → ramp → courtyard → back → Sankt Lars väg → park
level → shore path → Höje å valley, each checkpoint within 20 cm of the web's surface. The drawn terrain lies 1 cm under
the elevation grid on purpose (src/surroundings.js `terrainSurface`). Results: [#2280 verification](../verification/2280/README.md).

### Generated assets: rebuilt, not versioned (decided)

The three zones import to **249 MB** (248,848,382 bytes) (l1007: StaticMeshes 166 MB, Materials 35 MB, SceneImport asset 30 MB, level
6 MB). A re-import writes every package anew (new GUIDs), so each import that is committed stores the full size again
in Git LFS (GitHub Free: 10 GiB storage, 10 GiB download per month). **Recommendation: do not version generated
assets**; every Unreal checkout rebuilds them (export ≈ 2 min, import ≈ 2 min), and packaging (#2248) runs export +
import before cooking. `/Content/Lunden/Generated/` is Git-ignored. Hand-made content that
references generated assets (#2246 levels/Blueprints) would then reference them by path/tag, which the stable ids
make possible. **Decision (#2245, 2026-11-20; can be overturned in one sentence):** they are not versioned and
`/Content/Lunden/Generated/` stays Git-ignored. Alternatives if that changes: version them in LFS (budget ≈ 250 MB
per committed import), or shrink first (drop the `InterchangeSceneImportAsset`, decimate the heaviest furniture) and
re-measure.

### Screenshots

`tools/unreal-engine/python/screenshot_level.py <out dir> [zone]` renders fixed views of an imported level with a
SceneCapture2D and temporary sun/sky light (nothing is saved). It needs the GPU: run `UnrealEditor-Cmd.exe` directly
with `-run=pythonscript -AllowCommandletRendering` (commandlets otherwise load NullDrv and every render target is
"released"); `run-python.ps1` always passes `-nullrhi`. The first GPU run compiles the editor's SM6 shaders (about
20 minutes on the development PC, cached in the DDC afterwards; later runs take 20 s). The script waits for mesh and
shader compilation (`AutomationLibrary.finish_loading_before_screenshot`), hides the collision boxes (hidden in game
only, so an editor-world capture would draw them) and renders without Lumen and virtual shadow maps, which need many
frames to converge.

```text
"C:\Program Files\Epic Games\UE_5.8\Engine\Binaries\Win64\UnrealEditor-Cmd.exe" unreal\Lunden\Lunden.uproject -run=pythonscript "-script=C:/…/tools/unreal-engine/python/screenshot_level.py C:/…/unreal/Lunden/Saved/Screenshots" -AllowCommandletRendering -unattended -nosplash -nosound
```
