## Requirements

Engine: **Unreal Engine 5.8.x**, locked to **5.8.4** (latest stable hotfix 2026-10-20; 5.9 is only a preview),
installed with the Epic Games Launcher. A source build of the engine is not needed for a client game (a dedicated
server would need one; not planned).

The editor and its Python tests only need the installed engine. The packaging workstation also has the UE 5.8 Windows toolchain (Epic's
[Visual Studio setup](https://dev.epicgames.com/documentation/unreal-engine/setting-up-visual-studio-development-environment-for-cplusplus-projects-in-unreal-engine)
and [hardware/software specifications](https://dev.epicgames.com/documentation/unreal-engine/hardware-and-software-specifications-for-unreal-engine)):

- Visual Studio 2022 **17.14+** or Visual Studio 2026 (18.x) with the *Game development with C++*,
  *Desktop development with C++* and *.NET desktop development* workloads;
- MSVC v143 **14.38+** (14.50 recommended), Windows SDK **10.0.22621.0+**, .NET Framework 4.6.2 targeting pack;
- UnrealBuildTool runs on the .NET SDK bundled with the engine; a system .NET is not required.

The development PC (i9-10900K, RTX 3080, 32 GB RAM, Windows 11 Pro) is above Epic's recommendation for the editor.

### Install steps (done by the user; the Epic login cannot be automated)

1. **Epic Games Launcher** → sign in → *Unreal Engine* → *Library* → **+** next to *Engine Versions* → choose
   **5.8.x** → install to the default `C:\Program Files\Epic Games\UE_5.8`. In the engine's dropdown, turn off
   automatic updates so a new hotfix does not silently replace the locked version.
2. **Visual Studio 2022 Community** with the project's component list
   [`tools/unreal-engine/lunden-unreal.vsconfig`](../../tools/unreal-engine/lunden-unreal.vsconfig): download the bootstrapper
   https://aka.ms/vs/17/release/vs_community.exe and run, from the repository root on Windows,

   ```text
   vs_community.exe --config tools\unreal-engine\lunden-unreal.vsconfig
   ```

   (or *Visual Studio Installer → More → Import configuration* for an existing install). The file selects the
   CoreEditor, NativeGame (*Game development with C++*), NativeDesktop (*Desktop development with C++*) and
   ManagedDesktop (*.NET desktop development*) workloads, MSVC v143 x64/x86, Windows 11 SDK 22621, the
   .NET Framework 4.6.2 targeting pack, C++ diagnostic tools and `Component.Unreal.Ide` (IDE support for Unreal
   Engine). The separate "Unreal Engine installer" component is not included: the engine comes from the Launcher.
   VS 2026 also satisfies Epic's requirements.
3. Check: `powershell.exe -NoProfile -File tools/unreal-engine/check-environment.ps1` must end with
   `OK: the Unreal environment matches the project lock.`

`check-environment.ps1` deliberately checks only what a build needs: a VS 2022 17.14+/2026 instance with MSVC 14.38+, a
Windows SDK 10.0.22621.0+ and the .NET Framework 4.6.2 targeting pack. Other components of the `.vsconfig` that are
missing are listed for information; Unreal-specific VS components are never checked.

## Version lock

- `EngineAssociation: "5.8"` in `Lunden.uproject` makes the Launcher/editor pick the installed 5.8 engine.
- `unreal/Lunden/ENGINE_VERSION` holds the exact hotfix (`5.8.4`). `check-environment.ps1` (and every script that runs the
  engine) reads `Engine\Build\Build.version` and fails with exit code 3 on any other version:
  `ERROR: Wrong engine version: found 5.8.3 …, the project is locked to 5.8.4`.
- Upgrading (a new 5.8 hotfix, or 5.9 once it is stable) is a deliberate change in its own issue: update
  `ENGINE_VERSION` (and `EngineAssociation` for a minor version), rebuild, re-run the tests.

## No windows on the user's desktop (user, 2026-11-21)

Agents run everything hidden; the user works on the same PC. Never open a visible window:

- Unreal (editor commandlets, packaged game, tests): `-unattended -nosplash` plus `-RenderOffScreen` when frames are
  needed (screenshots, rendering tests) or `-nullrhi` when they are not. Never start the editor GUI or a game window.
- Windows Git: `git.exe -c core.editor=true` with `-m`/`-F` (an editor once opened on the desktop).
- PowerShell/other Windows tools from WSL: run as console processes (`powershell.exe -NoProfile -File …`); a tool that
  would open a window gets its headless flag or is started hidden (`Start-Process -WindowStyle Hidden`).

If a check genuinely needs a visible window, ask the user first.

## Where the Unreal checkout lives

The global WSL rule is to work in ext4 mirrors, but the Unreal editor, UnrealBuildTool and Visual Studio are
Windows programs: building a project on a `\\wsl.localhost\…` path is slow or fails. **Decision (#2243, can be
overturned in one sentence): Unreal work runs in a dedicated Windows clone,
`C:\Users\Olof\Documents\lunden-unreal-engine`**, made and committed with **Windows Git** (Git LFS 3.8.1). It is a
plain clone of GitHub, **not** the `winc` side of the WSL mirror (`C:\Users\Olof\Documents\lunden-3d-apartment`)
and **not** registered with `wsl-repo-sync`: the mirror must stay clean for the sync (see below), and engine output
(`Binaries/`, `Intermediate/`, `Saved/`, `DerivedDataCache/`) would otherwise sit in the synced tree. One-time setup:

```text
git clone --filter=blob:none https://github.com/solwation/lunden-3d-apartment C:\Users\Olof\Documents\lunden-unreal-engine
cd C:\Users\Olof\Documents\lunden-unreal-engine
git lfs install --local
git config lfs.fetchexclude ""
git lfs pull
```

The scripts refuse to run the engine on a WSL/UNC checkout (exit code 6) and only warn in `check-environment.ps1`.
For the first content-only cook, use a fresh Windows checkout. Earlier native or temporary
build targets in an old checkout’s ignored `Intermediate/` or `Binaries/` can make UAT
look for a project-specific editor receipt.

- WSL Git has **no git-lfs**. A `.uasset` committed from WSL would bypass the LFS filter and land in normal Git
  history. Commit Unreal binaries only with Windows Git (`"/mnt/c/Program Files/Git/cmd/git.exe"` from WSL, or
  Git for Windows directly) until git-lfs is installed in WSL.
- Text files (`.uproject`, `Config/`, `Content/Python/`, `tools/unreal-engine/`, this document) can be edited and committed
  from the ext4 mirror as usual; the LFS rules do not touch them.
- **LFS and the WSL mirror (verified 2026-11-20 with throwaway clones):** WSL Git without git-lfs checks out an LFS
  commit as the 129-byte pointer text and `git status` stays clean (`git hash-object` of the pointer equals the
  committed blob). A WSL push to an `updateInstead` mirror on `/mnt/c` writes the pointer too, and Windows Git in
  that mirror also reports it clean; a Windows Git checkout there keeps the pointer (`.lfsconfig` excludes
  `unreal/**`) and marks the `lockable` file read-only, which a later WSL push still replaces. **The one way to break
  the sync:** real LFS content in the mirror (someone runs `git lfs pull` or clears `lfs.fetchexclude` in
  `C:\Users\Olof\Documents\lunden-3d-apartment`). Both Gits then report the `.uasset` as modified, `updateInstead`
  rejects every push ("Working directory has unstaged changes") and `wsl-repo-sync` stops with a warning. Never
  pull LFS content into the mirror; Unreal work belongs in the dedicated clone.

## Scripts (`tools/unreal-engine/`)

All scripts are PowerShell (Windows PowerShell 5.1 or PowerShell 7), run on Windows and callable from WSL:

```text
powershell.exe -NoProfile -File tools/unreal-engine/check-environment.ps1
powershell.exe -NoProfile -File tools/unreal-engine/build-editor.ps1 [-Configuration Development|DebugGame]
powershell.exe -NoProfile -File tools/unreal-engine/run-python.ps1 tools/unreal-engine/python/smoke_create_asset.py [args…]
powershell.exe -NoProfile -File tools/unreal-engine/run-tests.ps1 [-Filter Editor.Python.Lunden.] [-WithRhi]
```

Run repository scripts on a Windows host whose existing policy permits them. Every engine script
takes `-EngineDir <root>` (or the environment variable `LUNDEN_UNREAL_ENGINE_ROOT`); otherwise the engine is found through the
registry (`HKLM\SOFTWARE\EpicGames\Unreal Engine\5.8`), the Launcher's `LauncherInstalled.dat` and finally the
default path. Logs go to `unreal/Lunden/Saved/Logs/<script>-<time>.log` and test reports to
`unreal/Lunden/Saved/Automation/<time>/` (both ignored by Git).

| Script | Runs | Success means |
|---|---|---|
| `check-environment.ps1` | nothing; reports project, engine, VS/MSVC, SDK, .NET | exit 0 and `OK: …` |

## Git LFS (Unreal only)

`.gitattributes` in the repository root puts **only files under `unreal/`** in Git LFS:

- `unreal/**/*.uasset` and `unreal/**/*.umap`: `filter=lfs diff=lfs merge=lfs -text lockable`;
- source art and import files under `unreal/`: `*.fbx *.obj *.glb *.exr *.hdr *.png *.tga *.psd *.tif *.tiff
  *.jpg *.jpeg *.wav *.ogg *.mp3 *.mp4` (LFS, not lockable).

**Never add an LFS rule outside `unreal/`.** GitHub Pages cannot serve LFS files and the Pages checkout does not
fetch them, so an LFS-tracked web file (`models/*.glb`, `music/*`, `textures/*`, `data/*`, `icons/*` …) would be
published as its pointer text ([GitHub: Git LFS and Pages](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-git-large-file-storage)).
Check with `git check-attr -a -- <path>`: web paths must print nothing, `unreal/**/*.uasset` must show `filter: lfs`
and `lockable: set`.

`.lfsconfig` sets `lfs.fetchexclude = unreal/**`, so agent clones, cloud sessions and CI never download Unreal
content. The Unreal checkout opts in locally, once:

```text
git config lfs.fetchexclude ""
git lfs pull
```

**Quota (user decision, non-blocking now; #2242 point 3):** GitHub Free includes 10 GiB LFS storage and 10 GiB
download per month ([billing](https://docs.github.com/en/billing/concepts/product-billing/git-lfs)). Every saved
version of a binary `.uasset` is stored in full, and every clone that pulls LFS downloads it. Recommendation: start
on Free, report the LFS size in each Unreal delivery (`git lfs ls-files -s`), add large source files (raw EXR,
photos) only when they are actually used, and keep generated imports (#2245) out of Git where possible.

## Claude Code and MCP

Stable automation does not depend on MCP: headless Python (`run-python.ps1`), commandlets, Automation Tests
(`run-tests.ps1`) and later `RunUAT BuildCookRun` are the primary route. MCP is a complement for interactive work in
an open editor.

- **Plugins in `Lunden.uproject`:** `ModelContextProtocol` (the server, "Unreal MCP", experimental in UE 5.8) and
  `AllToolsets` (mounts the toolset plugins; without it the server exposes no tools). Both exist in 5.8.4 under
  `Engine/Plugins/Experimental/` (verified). Names first came from Epic's
  [setup.md](https://github.com/EpicGames/unreal-engine-skills-for-claude-code-plugin/blob/main/skills/unreal-mcp/references/setup.md).
- **Claude Code plugin** (Epic, MIT): https://github.com/EpicGames/unreal-engine-skills-for-claude-code-plugin.
  Optional: `/plugin install unreal-engine-skills-for-claude-code@claude-plugins-official`. It ships skills
  (`unreal-mcp`, `unreal-skill`, `create-toolset`) and a SessionStart hook that needs `bash`; no MCP server of its
  own. Not installed by #2243.
- **Start the server** per session: editor console `ModelContextProtocol.StartServer [port]` (stop:
  `ModelContextProtocol.StopServer`), or start the editor with `-ModelContextProtocolStartServer`
  (`-ModelContextProtocolPort=N` to change the port). Auto-start is per user only
  (`Saved/Config/WindowsEditor/EditorPerProjectUserSettings.ini`, `[/Script/ModelContextProtocolEngine.ModelContextProtocolSettings]`
  `bAutoStartServer=True`) and deliberately not in the shared `DefaultEditor.ini`; commandlets never auto-start it.
- **Verified 2026-11-20:** the editor logs `Created new HttpListener on 127.0.0.1:8000`; the listener binds loopback
  because `[HTTPServer.Listeners] DefaultBindAddress` defaults to `localhost` (leave it unset; `any` would expose it).
  `initialize` → protocol `2025-06-18`; `tools/list` returns the three meta-tools `list_toolsets`, `describe_toolset`
  and `call_tool` (tool search), and `list_toolsets` lists the toolsets (Automation tests, config settings, editor,
  logs, …). The [forum report](https://forums.unrealengine.com/t/5-8-experimental-modelcontextprotocol-mcp-server-instantly-drops-connections/2729488)
  of 5.8 dropping connections did not reproduce over plain HTTP requests.
- **From WSL:** this PC runs WSL2 in **NAT** networking (`wslinfo --networking-mode` = `nat`). A WSL process cannot
  reach Windows loopback (`curl http://127.0.0.1:8000/mcp` → connection refused; the host IP times out because the
  server is not bound there). Mirrored networking or a wider bind would change Windows/WSL settings or expose the
  port, so instead `tools/unreal-engine/mcp-bridge.py` is a stdio MCP server for Claude Code that forwards each
  JSON-RPC message with the Windows `curl.exe` (WSL interop) to `127.0.0.1:8000`; the server stays loopback-only.
  Verified from WSL: `initialize`, `tools/list` and `describe_toolset` through the bridge. Register it **locally**
  (machine config, never committed), from the ext4 checkout:

  ```text
  claude mcp add --scope local unreal-editor -- python3 /mnt/c/Users/Olof/Documents/lunden-unreal-engine/tools/unreal-engine/mcp-bridge.py
  ```

  Claude Code running on Windows can instead connect directly: `claude mcp add --transport http unreal-editor
  http://127.0.0.1:8000/mcp`. Check with `/mcp` and a read-only `list_toolsets`. Limits of the bridge: one request
  at a time, no server-initiated stream. Without a running editor every call returns a clear error.
- **Security boundary:** the server has **no authentication**; any process of the same Windows user (and, through
  the bridge, of the WSL user) can call it. `ProgrammaticToolset.execute_tool_script` runs arbitrary Python in the
  editor. Do not run the MCP server on a shared machine, never expose the port, commit before long MCP sessions and
  review the diff. Stop the server (or the editor) when done.

## Parallel work: levels and Blueprints

Binary Unreal assets (`.umap`, `.uasset`) cannot be merged. These rules let the porting issues (#2247; the
[issue table](unreal-inventory.md#porting-issues-release-1) names each one's write area) run at the same time.
They apply together with the [hidden-window rule](#no-windows-on-the-users-desktop-user-2026-11-21): every step
below runs headless.

**Ownership.**

- **One owner per binary asset, level and content folder at a time**, named in the owning issue's "Ägarskap"
  section. An issue writes only the `/Game/Lunden/<Area>/` folders, levels and builder scripts it names. It reads
  other areas' assets and references them by path or actor tag, never by editing them. Ownership passes only by
  explicit handover in both issues (for example from the pilot #2246 to the issue that takes over its assets).
- **One owner per zone level.** The world is a persistent map, `/Game/Lunden/Maps/L_Lunden`, with one sub-level per
  zone and area. The issue that owns the persistent map rebuilds it with its composition script from a text list of
  sub-levels. Other issues add their own line to that list and never open the persistent map. Each sub-level
  has exactly one owning issue. Generated zone levels (`/Game/Lunden/Generated/<zone>/Level_<zone>`) stay owned by
  the importer, and an area that needs to change imported actors makes a derived sub-level through its own builder
  under `Generated/<Area>/`, as the pilot's door builder does.
- **One file per actor (OFPA) is optional, not the default.** The importer writes plain levels, and plain
  sub-levels per zone are what the pilot verified. A hand-made sub-level that several issues will fill over time may
  turn on external actors (`__ExternalActors__/`, one `.uasset` per actor) so that owners of different actors do not
  collide. Its level file still has one owner. World Partition is not used, because a World Partition map cannot
  hold streamed sub-levels. Decide again in its own issue if the outdoor world outgrows sub-levels.
- **Seams instead of shared assets.** When another area must hook into an owned class (GameMode, PlayerController,
  character, HUD, avatar, door), the owner exposes an extension point that is read from text. Examples are a JSON
  list of component classes that its builder adds or Blueprint event dispatchers that others bind to at run time.
  The other issue changes only that text or binds from its own assets.

**Locking (Windows Git in the dedicated Unreal clone).**

1. Check `git lfs locks` and the owning issue before touching a binary. Someone else's lock means stop; never use
   `git lfs unlock --force` on another owner's lock without a handover recorded in both issues.
2. `git lfs lock <path>` for every `.umap`/`.uasset` you will write, including assets a builder regenerates. With
   `lockable`, an unlocked file is checked out read-only, so a builder that forgot the lock fails early.
3. Commit and push, then `git lfs unlock <path>`. Do not keep a lock across a pause or a handover. Release it, or
   hand it over explicitly.
4. Text files (`tools/unreal-engine/**`, `Config/*.ini`, `Lunden.uproject`, `shared/`, `cloudflare/`, docs) are not
   locked. Several issues may change them by ordinary rebase. Each issue lists the shared text files it touches and
   keeps its change additive.

**Blueprint/Python split in the content-only project (#2268).** The project has no C++ module and no plugin with
its own binaries, so the editor and the packaged game load only Epic-signed code.

- **Runtime logic is Blueprint**, using engine classes, components and Epic-shipped plugins that are enabled in
  `Lunden.uproject`. Keep each Blueprint small and owned by one area: components and function libraries rather than
  one large actor.
- **Editor Python is the source of every hand-maintained asset.** Each area has a builder,
  `tools/unreal-engine/python/build_<area>.py`, that creates or updates its Blueprints, graphs, input assets,
  materials and sub-levels headless (as `build_player.py` and `build_pilot_doors.py` do). The committed `.uasset`
  is the builder's output: review the script diff, regenerate with the lock, commit both. Agents never edit
  assets in the editor GUI.
- **Builder stamps do not depend on line endings (#2309).** `.gitattributes` keeps `tools/unreal-engine/**/*.py`
  and `*.json` LF in every checkout, so a Windows clone with `core.autocrlf=true` gets the same `--check` result as
  WSL instead of wanting to resave committed assets. An existing clone checked out before the rule needs its files
  re-checked out once (`git rm -r --cached -q tools/unreal-engine && git reset -q --hard`, on a clean tree). Builders
  whose stamp is local (`build_exterior/l1007/site/vegetation.py`) and the importer's `material-map.json` hash also
  normalise CRLF to LF before hashing. `build_lighting.py` still hashes its raw bytes, because its spec hash is
  stored in the committed `BP_LundenSky`: changing it would force a locked rebuild of `/Game/Lunden/Lighting`.
  Normalise it (`.replace(b"\r\n", b"\n")`) the next time that script changes anyway and its assets are rebuilt.
- **Python never ships.** The packaged game runs Blueprints and assets only. Editor Python covers import, builders
  and tests (`tools/unreal-engine/tests/test_<area>.py`, run through `PythonAutomationTest` in Play In Editor).
- **Shared values come from data.** Read measurements, IDs and rules from the #2245 export (`measurements.json`,
  actor tags) or from DataTables and DataAssets that a builder fills from it. Do not hand-copy web numbers into
  graphs.
- **A missing engine capability is a decision, not a workaround.** If a feature needs something no Epic-shipped
  plugin exposes to Blueprint, such as a general WebSocket client, stop and ask the user on the issue
  (`user-question`). Adding native code reopens #2268.
- `Content/Lunden/Generated/` is written only by scripts: the #2245 importer and the derived-level builders, each in
  its own `Generated/<folder>/`. Hand edits there are lost on the next run.
- Different tools folders can be worked on in parallel (`tools/unreal-engine/export*`, `tools/unreal-engine/package*`,
  `unreal/Launcher/`; #2242).

standing headroom over the eye (half height 59 cm); the web has no crouched body height. Since #2300 Shift is 480 cm/s
outdoors (`runOutdoor`), the surface under the feet is known and the player can sit and lie down
([Surface, outdoor sprint, rest and death](#surface-outdoor-sprint-rest-and-death-2300)).

**Mouse look (#2294).** `src/main.js` turns the view by `PLAYER.mouseSens` (0.0013 rad, 0.0745°) per pixel of mouse
movement, up looks up. The graph multiplies the raw MouseX / MouseY counts by `LookDegrees` (that value in degrees)
into `AddControllerYaw/PitchInput`. Two engine settings from the 5.8 template are switched off in
`Config/DefaultInput.ini`, and `build_player.py` refuses to build or pass `--check` when either is back:
`bEnableLegacyInputScales=False` (with it on, `BaseGame.ini` `InputPitchScale=-2.5` inverted the pitch and
`InputYawScale=2.5` multiplied the yaw) and `Sensitivity=1` on the MouseX / MouseY `AxisConfig` (the template's 0.07
reached the look actions too). The pilot therefore turned at 0.175 times the web's rate with the pitch inverted; now
one count is 0.0745° on both axes. The mouse speed and inverted-Y settings are #2286's ([Menu, settings and compass](#menu-settings-and-compass-2286)).

**Pitch limits (#2370).** Web mouse and touch look use `PLAYER.pitchLimit` in radians. The scene export carries it
as `spawn.player.pitchLimit`. From a fresh export, `build_player.py` converts it to degrees and sets
`ViewPitchMin/Max` on `BP_LundenCameraManager`. The production controller selects this camera class at spawn.
Unreal's normal rotation update clamps free look and a restored save to ±83.079° (±1.45 rad). Sitting and lying
temporarily apply their own exported ranges within those stops. Standing up restores the camera's original limits.
A format-1 export predating `pitchLimit` uses the historical 1.45 rad limit. An explicitly invalid value fails the build.
`python3 tools/unreal-engine/tests/player_pitch_legacy_test.py` exercises this compatibility path.
With the local web server running, `node tools/unreal-engine/tests/player-pitch.cjs <web-url> <measurements.json>`
checks pointer-locked mouse input against the export at both stops and when turning away from each one. The builder's `--check` verifies the controller binding
and both camera defaults. After rebuilding the Player assets, run `test_player` for both mouse stops, `test_save`
for an older out-of-range facing and `test_player_world` for the sofa, bed and standing view.

**Fall damage** (`src/player.js` landing, `src/falldamage.js`, `src/combat.js` `fall`). A fall starts when the
character enters Falling (take-off of a jump, or the ledge it walked off) and its drop is that capsule height minus
the landing height. Unreal only falls in free drops, since stairs and steps up to 45 cm stay in Walking, so the web's
gap under the feet is never smaller than the drop. The rule is therefore: drop over `FallMaxReport` (100 m) costs
nothing (the web reports no damage), over `FallFatal` (6 m) costs `MaxLives`, over `FallHurt` (3 m) costs
ceil(`MaxLives` / 2), else nothing. Lives drop by the damage, and a death (damage ≥ lives) refills them and counts
`Deaths`; `LastFallDrop` and `LastFallDamage` hold the latest landing for #2293's shared life and the HUD. A death
then blacks out and wakes outdoors (#2300, below); suit protection stays with #2293/G08. Floor checks use a flat base
(`use_flat_base_for_floor_checks`): with the round capsule bottom the character sank up to 17 cm down a ledge before
falling, and the drop came out short.

**Extension point.** `tools/unreal-engine/player-extensions.json` (`formatVersion` 1) lists components as
`{target: character | controller, name, class, owner, what}`. `build_player.py` adds each missing row's component to
`BP_LundenPlayer` or `BP_LundenPlayerController`. It removes components it added earlier whose row is gone, recorded
in the asset metadata `Lunden.PlayerExtensions`, and leaves every other component alone. #2285, #2286, #2287, #2288
and #2292 add their rows here and never open the player Blueprints.

**Idempotency.** The builder stores a hash of its inputs (export values, extension rows, the script itself) as
`Lunden.SpecHash` on `BP_LundenPlayer`; a run with the same inputs logs `unchanged, nothing saved`. `--check` fails
when the assets are missing, the hash differs or a pilot asset is still in its old folder. A changed input rebuilds
the character's event graph from scratch and rewrites the defaults.

  and not behind the first thing a visibility trace hits. `BeginRest` then stops walking and collision and glides the
  eye to the spot over `REST.move` with smoothstep, turning to the spot's start view (`Rest.begin`). After that it
  clamps the camera manager's view to the spot's yaw ± the kind's yaw and its pitch range (`Rest.clampLook`). E,

  `standUp`. The keys are read with `WasInputKeyJustPressed`, so E still opens doors through the controller.

  included. Of the web's rest targets, 34 spots (7 for lying) on 20 exported pieces are in `spawn.rest`; four targets (two café chairs

- **Death.** A landing that kills (#2284's rule) calls `Die()`, which is also #2293's hook for other deaths. `Die()`

  random point in a random region and checks it). The player faces the wake yaw with a level view, input comes back
  and the black fades out over `back`. *Not ported:* the cover text, the landing sounds and jolt, and the red flash
  of a non-fatal hurt. The HUD and sounds belong to #2293 and #2287.

The web shows the Christmas tree only from `XMAS_TREE.season.from` to `.to`, inclusive across the new year (1 Dec –
6 Jan; `src/christmas.js` `inChristmas`). This is the minimal part of G20 (Later in the

- **Data.** The exporter marks the tree `extras.seasonal = {what, from, to}` from `src/config.js`. It uses the web's

  the tree receive their furniture's tags when `build_lighting.py` generates `Level_lighting`.

  the cushions in under rain clouds (`overcast` > 0.6), which a date window cannot carry; that is weather (#2331).

- **Rule, in one place.** `BPC_LundenSeasons` (ActorComponent, built by `build_seasons.py`) has `InSeason(Year, Month,

  `ApplySeason(Year, Month, Day)` shows every `seasonal` actor with collision inside its window and hides it without
  collision outside it; an actor without readable window tags is left alone. A new seasonal item needs only the

## Save file (#2288)

The web keeps the player's name (`lunden.name`), opaque id (`lunden.playerId`, a `crypto.randomUUID()`), look code
(`lunden.avatar`), settings and place (`src/resume.js`, `lunden.playerWorld`) in browser storage
([storage](storage.md#local-player-profiles-1515)). The Windows game keeps them in one versioned SaveGame slot,
`LundenSave`, written by the engine to `<user dir>\Saved\SaveGames\LundenSave.sav`. The launcher starts the game
with `-UserDir=%LOCALAPPDATA%\Lunden` (`Lunden-Test` for the test channel), so the file lives outside the
installation, is never part of a version tree and is kept by a default uninstall ([launcher](#windows-launcher-2249)).
In the editor it is `unreal/Lunden/Saved/SaveGames/LundenSave.sav`. #2288 owns `/Game/Lunden/Save/`, `build_save.py`,
`tests/test_save.py`, `tests/save-v0.sav` and the `Save` row of `player-extensions.json`.

- **`SG_LundenSave`** (SaveGame): `SaveVersion`, `PlayerName`, `PlayerId`, `LookCode`, `PlaceMap`, `PlaceLocation`
  (cm), `PlaceRotation` (the control rotation: pitch and yaw) and `Settings` (string → string).
- **`BFL_LundenSave`** (function library) is the interface for other areas: #2286 uses `GetSetting(Key, Default) →
  Value, Found` and `SetSetting(Key, Value)`, #2291 `GetLookCode`/`SetLookCode`, #2292 `GetPlayerName`/`SetPlayerName`
  and `GetPlayerId`. Every call reads the slot and every setter writes it back at once, so callers keep no copy and
  never overwrite each other. `LoadSave()` always returns a save: a missing or unreadable slot becomes a new save with
  a new id, written at once. Settings are strings under keys the owning area chooses (for example
  `mouse.sensitivity`); convert numbers with the string conversion nodes. `NewPlayerId()` makes a lower-case
  8-4-4-4-12 id like the web's.
- **`BPC_LundenSave`** rides on `BP_LundenPlayerController` (`player-extensions.json` row `Save`). At BeginPlay it puts
  the possessed pawn back at the saved place and facing when the save was made on the same map (`K2_TeleportTo`, which
  refuses or nudges a spot that something now blocks; the body takes the yaw, the view pitch and yaw), retrying every
  `RetrySeconds` until a pawn is possessed. Then it saves the place every `SaveIntervalSeconds` (2 s, like the web's F5
  record) and at EndPlay. A save from another map (the pilot map, a test level) is not applied.
- **Versions and migration.** `SaveVersion` defaults to 0 on the class and a SaveGame stores only properties that
  differ from the defaults, so a file written before the field existed reads as 0. New saves get `CurrentVersion()`
  (1). `MigrateSave` brings an older save up one step at a time and `LoadSave` writes the result back; 0 → 1 adds the
  player id. A new version adds a step there, keeps old field names and types (a renamed field reads as empty) and a
  frozen file of the old layout under `tests/`, as `save-v0.sav` is for version 0. A save from a newer build (after a
  launcher rollback) is read as far as this build knows it; fields it does not know are dropped at its next write.
- **Not in the save:** the home and life simulation (G13, later), cloud storage, several local profiles (the web's
  `lunden.players.v1`; one player per Windows user for now) and the web's two-minute "Ladda om" record (the game
  always resumes at the last place).

handling and still rewrites the slot on purpose. The game's save behaviour is unchanged.

## Footsteps, wind and outdoor sound (#2287)

The web synthesises every sound with Web Audio and plays no sound files (`src/audio.js`). G09's release-1 part brings
three of them to Unreal as procedural MetaSounds with the web's own numbers: footsteps that change with the surface,
the outdoor wind and the outdoor bed (Höje å and the far city), plus a simple room reverb. #2287 owns
`/Game/Lunden/Audio/`, `build_audio.py`, `export-audio.mjs` with its `audio-params.json`, `tests/test_audio.py`,
`tests/test_audio_render.py`, `tests/audio-render-compare.py`, the `Audio` row of `player-extensions.json` and the
sound classes of the three `volumes` rows of `ui-extensions.json`.

- **Numbers from the web's modules.** `export-audio.mjs` imports `src/config.js` (`FOOTSTEPS`, `PLAYER.strideWalk/strideRun`,
  `WIND_SOUND`, `WIND.power`, `AMBIENT_BED`, `ROOM_REVERB`, `SEASON`), `src/riverbridge.js` `riverPath` and the teleport
  limit of `src/main.js` `footsteps()`, and writes `tools/unreal-engine/audio-params.json`. The file also holds the web's
  own answers of `footsteps.js pickStep` (1,152 cases), `windsim.js windPower`, `windsound.js windStrength / gustAt /
  windSoundParams` (324 cases) and `ambientbed.js riverBabbleParams / trafficLevel / cityHumParams / distToPolyline`.
  `--check` fails when the file no longer matches the web. `build_audio.py` turns the constants into MetaSound node
  defaults and into graph literals, and the tree feet come from the export (`measurements.json` `vegetation.trees`).
- **Footsteps** (`MS_LundenStep_<profile>`, one one-shot MetaSound per `FOOTSTEPS.profiles` entry: `wood` = parquet,
  `hard` = tile, paving, stone and the garage, `grass`, `gravel`, and `stair`, `wet`, `snow`, `snowCold`, `leaves`).
  Each is `synthFootstep` built by the MetaSound builder. The sine body glides exponentially from `hz × v` to `endHz` over
  `duration`. White noise goes through a low-pass biquad at `cutoff`, and the web's Q (dB for a low-pass, as the Web
  Audio spec defines it) becomes the exact Unreal bandwidth for that cut-off. Both rise linearly to their peak × `v` over
  `attack` and fall exponentially to `releaseFloor` at `duration`. Then come the `grain` crackle and the `partial`
  (squeak, stair ring). `v` = 1 ± `variation` is drawn on every play. *Approximations:* the envelopes are block-rate
  (5.3 ms segments, interpolated). The crackle is a triangle between one random trough per step and 1, where the web
  draws a new trough each time. The web's last 30 ms from −80 dB to 0 is left out.
- **`BPC_LundenAudio`** (character, `player-extensions.json` row `Audio`). Every tick it adds the ground covered while
  `IsMovingOnGround`. A jump of more than `teleport` (0.5 m) between frames counts as nothing. A step sounds every
  `StrideWalk` (62 cm), or every `StrideRun` (95 cm) while `Running` (Shift). The step asks #2300's
  `BPC_LundenStepSurface.FeetInfo` for the class and runs the transcribed `PickStep` (stair in a core, snow, wet hard
  ground, autumn leaves on grass or gravel, else the surface). Then it plays that profile's MetaSound with
  `PlaySound2D` at `FOOTSTEPS.gain` × the web master, and records `StepCount`, `LastProfile` and `LastStepSound`. The weather comes from
  the world's `BP_LundenSky` (`WindSpeed`, `Wet`, `Month`, `Hour`; `UseSky` off lets a test set them). `SnowCover` (0)
  and `Temperature` (10 °C, the web's `weather.temp ?? 10`) wait for snow cover and temperature to be ported, so no
  snow steps sound yet.
- **Wind and outdoor bed** (`MS_LundenWind`, `MS_LundenAmbience`, looping, started with `SpawnSound2D` at BeginPlay).
  Every `WIND_SOUND.every` (0.25 s) the component computes `windSoundParams` from the sky's wind and the web's gust
  sweep. The other inputs are the month's leaf cover and `treeNearness` to the exported trees. The component also
  computes `riverBabbleParams` from the distance to Höje å's centre line and `cityHumParams` from the hour. It pushes
  them with `SetFloatParameter`, and the MetaSounds ease to them over `WIND_SOUND.ease` / `AMBIENT_BED.ease`.
  `Indoors` is `not FeetInfo.Outdoor` (a flat, stairwell or garage), which applies the web's one indoor model: lower
  gain and a lower low-pass ceiling. *Approximations:* the ease is linear (`InterpTo`) where the web's
  `setTargetAtTime` is exponential. Tree nearness uses every exported tree, where the web uses `treeFeet` alone. A
  moving cut-off uses the engine's Q-to-bandwidth node, which leaves out the small `w0 / sin w0` correction.
- **Wind through an open sash** (#2320). The audio builder uses the existing interaction IDs, top pivots and lower
  rail positions from the window export. Each open sash has a stationary mono `MS_LundenWindowWind` at its centre.
  The sky's wind speed and gust set its low-pass and gain every 0.25 s. Closing one sash fades that voice in 0.4 s.
  The inverse attenuation matches the web's 1.2 m reference distance and 1.2 rolloff up to Unreal's 50.2 m cull
  distance. `test_window_audio.py` exercises two sashes in the composed map and changes the sky's wind. Running
  it with the silent mixer settings from `test_audio_render.py` also checks live voice identity and position.
- **Room** (*guess*, a simple form of `ROOM_REVERB`'s convolvers). `ZoneFor` is `indoorRoomClass` from the same surface
  class: a core is `concrete`, an indoor hard floor is `bright`, any other indoor floor is `soft`. Outside that,
  `roomreverb.js`'s courtyard rectangle gives `courtyard`, and the rest is `open`. A change of zone calls
  `ActivateReverbEffect(RE_Lunden<Zone>)`, or `DeactivateReverbEffect` for open, over `ROOM_REVERB.fade`. Each
  `RE_Lunden*` takes decay = `rt60`, gain = `wet`, late delay = `pre`, HF decay ratio = `damp[1] / damp[0]`, and for the
  courtyard the first slap echo as the reflections.
- **Sound classes and volumes.** `SC_LundenMaster` (root) > `SC_LundenEffects` (2D reverb send 1, as the web sends
  every effect to the room) > `SC_LundenAmbience` (send 0: the beds are dry on the web) and `SC_LundenMaster` >
  `SC_LundenMusic`. The steps are in Effects, the loops in Ambience. The menu's three sliders (#2286) now apply to
  Master, Effects and Music, and a slider applies to its class's children too. The engine's own
  `/Engine/EngineSounds/Master` is not the root, because a mix override reaches only the classes in its `ChildClasses`
  and that engine asset cannot list project classes. A sound added later should use one of these classes, since a sound
  without a class plays in the engine's Master, outside the Huvudvolym slider.
- **Decided here (can be overturned in one sentence).** No `Maps/Zones/Audio` sub-level: the web's beds follow the
  listener and its rooms come from the surface data, so the sources live on the player and `L_Lunden` is untouched.
  Every path carries the web's unmuted master gain (0.8): the step volume, the wind bed and the river/city bed in
  their MetaSounds, `RainGain` and the window voices. The engine's Master and Effects sliders still scale them.
  `DefaultEngine.ini` sets Web Audio's mixing laws (#2320): a mono 2D source reaches both channels at full level
  (`MonoChannelUpmixMethod=FullVolume`; the engine's unset default is Linear, 0.5 each), a positioned source pans
  with the equal-power law (`PanningMethod=EqualPower`, the web's `PannerNode` `equalpower`), and no platform headroom
  is taken (`[Audio] PlatformHeadroomDB=0`; `BaseWindowsEngine.ini` has −3 dB). Sources: `AudioMixerChannelMaps.cpp`,

- **Builder findings (5.8.4).** The MetaSound builder works headless (`MetaSoundBuilderSubsystem` +
  `MetaSoundEditorSubsystem.build_to_asset`). `BuildToAsset` only creates assets: the builder's own overwrite refuses a

- **Not ported:** the other weather sounds (hail, thunder), snow-cover and temperature steps (#2331), other

  *Assumption:* the web's clear sun 3.0 is 20 lux in Unreal (`SUN_LUX`, #2386; the pilot's 8 lux left sun shadows
  invisible next to the fill); the moon and the sky's scattering scale with it.
  Outputs: `SunDirection`, `MoonDirection` (unit vectors towards the body, Unreal axes), `SunElevation`, `Daylight`,
  `MoonIllumination`.
- **Sky and fill.** `SkyAtmosphere` lit by both directional lights, a real-time captured `SkyLight`,
  `ExponentialHeightFog` (denser and greyer under rain or snow, as the web greys sky and fog) and Epic's
  `VolumetricCloud` material (since #2307 with weather-driven coverage). Sky-light scale 2 and fog grey are *guesses*
  by eye against the web pictures.
- **Clear night sky (#2366).** The two stored START exposure trials put the web's sky luminance between
  the game exposure and +1.76 EV. The sky material applies a fitted +1.53 EV (*guess*) to the atmospheric
  background at astronomical night. The correction fades out with cloud cover and between astronomical and
  civil twilight. Run the paired captures and `crop-stats.cjs <out> <crops.json> --check-lighting` to check
  the three START sky crops and the accepted living-room and upper-floor views against 0.8–1.25 × the web.
  Measured after #2396's tone mapping, on ea08ec2d: the night sky 1.22 × the web (0.59 before), the day and rain skies
  1.13 and 0.87, and the 22:00 and 14:00 room frames 0.82–1.06 ([#2366 pairs](../verification/2366/README.md)).
- **Daylight indoors, the sky's brightness and the exposure (#2313).** Measured with `crop-stats.cjs` against the web,
  the 14:00 living room was 0.26 × and the rain sky at START 0.37 × the web's mean luminance. The web lights every
  surface with its hemisphere light (`LIGHTING.sky` overcast.hemi 2.0 → clear.hemi 1.5, × daylight, + `DAY.nightAmbient`,
  × (1 − 0.3 overcast)) and its flat `ambient`, both unshadowed, so its rooms are almost as light as the street; Unreal's
  captured sky light reaches a room only through its windows. Three changes (and the lamps' candela, below), all *guesses* set by the
  [#2313 pairs](../verification/2313/README.md):
  - **Fill.** The ambient cubemap `T_LundenHemisphere` (the web's hemisphere colours) gets the web's `ambient` plus
    `HEMI_SHARE` (0.72) × the web's hemisphere value; its post-process weight is that fill ÷ `AmbientRef`, an upper bound
    of the fill, which is also the component's intensity. The cubemap is not scaled by the exposure (UE adds it
    outside the pre-exposure: a −1 EV trial left the night street, lit only by it, unchanged), so it behaves like the
    web's flat light in display terms and carries the web's exposure itself (× web exposure ÷ 1.5) and the hemisphere's
    night colour (`daycycle.js` blends its sky colour `0xeaf3ff` to `0x6b7da8` by 1 − daylight; the weight takes the
    luminance ratio averaged over sky and ground, `HemiNight` 0.56). Without these two terms the 22:00 rooms were lit
    mostly by a neutral fill and came out grey-white (R/B 1.11 against the web's 1.50).
  - **Sun against the fill (#2386).** The fill sits outside the exposure and the sun inside it, so at 8 lux a web unit of
    sun reached the screen about 11 × weaker than a web unit of fill: sunlit and shaded brick differed by 1.1–1.4 × where
    the web shows about 2 × (its December patio). `SUN_LUX` 20 and `CLEAR_FILL` 0.75 (× the web's clear `ambient` and
    `hemi`) bring the sun's shadows back and keep the 14:00 pairs within 0.8–1.25 × the web; rain, 22:00 and the stairs
    do not change ([#2386 pairs](../verification/2386/README.md)). Shadows were never missing from the captures alone:
    `r.Shadow.Virtual.Enable 0` (cascaded shadow maps for one-shot captures) and the game's virtual shadow maps gave the
    same picture.
  - **Sky.** `UpdateSky` sets the atmosphere's `SkyLuminanceFactor` to `SKY_LUMINANCE` (9 × 8 ÷ `SUN_LUX`) by a clear day,
    blended to `SKY_OVERCAST` (8 ÷ `SUN_LUX`) at full overcast, so the sky keeps #2313's level whatever the sun's lux:
    the web paints a brighter sky than a physical atmosphere next to its sun.
    Under rain the web's sky is a fixed light grey (`OVERCAST`) that does not dim with the sun; in Unreal that grey is
    the height fog's inscattering, `FOG_GREY` (now 10, for the locked exposure; #2283's 0.6) × overcast. A trial that
    instead divided the sky factor by the sun's cut made the atmosphere show blue through the rain deck. The sky light's
    intensity is `SkyScale` × (1 − 0.3 overcast), without #2283's division by the cut.
  - **Exposure, locked.** The web has no eye adaptation: its tone-mapping exposure follows the sky (`DayCycle`:
    overcast.exposure 1.0 → clear.exposure 1.5 by daylight × (1 − overcast); the window term `WINDOW_LIGHT.exposure`
    0.05 is left out). The `Weather` post process is manual at `EXPOSURE_BIAS` (−2.55 EV, the web's exposure 1.0) and a
    third component, `Exposure` (priority 1), overrides the bias with +log2(1.5) at the blend weight
    ln(web exposure) ÷ ln(1.5), so the game's exposure is the web's rule. #2283's histogram auto exposure (EV100 −4 … 3)
    was compared on the same shots and rejected (see the pairs): metering each view, it made the dusk-lamp living room
    and the night street far brighter than the web's. Scene captures do not take the world's exposure, so
    `capture_lighting.py --exposure=game` sets the same bias (`game_bias`: the engine's lerp of the two components);
    `--exposure=histogram` renders the rejected auto exposure and `--set` / `--bias` run calibration trials.
  - **Result** (Unreal ÷ web, mean luminance): the 14:00 living room 1.01 (before 0.26), START's rain sky 1.00 (0.37),
    the 22:00 living room 0.83 and upper floor 1.21 with all lamps (#2307: 0.76, 1.15), the dusk-lamp living room 0.88,
    the clear sky 1.20. `CANDELA_PER_WEB` went from 1 to 2.8 to keep the evening rooms there under the darker exposure.
    START's whole pictures are about 2.3 × the web, because its façades and paving still render near-white.
  - **Tone mapping (#2396).** The web renders with `THREE.NeutralToneMapping` (Khronos PBR Neutral) and writes sRGB;
    Unreal's default filmic tonemapper crushed the darks and paled the brights. `M_LundenNeutralTonemap`
    (`python/neutral_tonemap.py`, built by `build_lighting.py`) replaces the tonemapper (`BL_ReplacingTonemapper`, a blendable
    of the `Weather` component) with three.js r170's `NeutralToneMapping` and `sRGBTransferOETF`, transcribed: the
    exposed colour is `PostProcessInput0` × `EyeAdaptation` (the input arrives without Unreal's pre-exposure; also
    dividing by `View.PreExposure` made it ignore the exposure). Not carried: bloom, vignette, film grain, colour
    grading and local exposure, none of which the web has. Cost: one full-screen pass of a few ALU per pixel in place of
    the tonemapper's own pass (no LUT). `tests/neutral_tonemap_probe.py` + `tests/check-neutral-tonemap.cjs` render 50
    emissive patches (0–10 grey, colours up to 6) and compare them with three.js 0.170.0 itself: within 1/255, and the
    exposure falls by 2.000 EV between bias 0 and −2. `EXPOSURE_BIAS` was measured again under it and stays
    ([#2396 pairs](../verification/2396/README.md)). Captures must show the displayed picture: `render_view` and
    `capture_lighting` take `SCS_FINAL_COLOR_LDR` into an RGBA8 target at `target_gamma` 2.2 (as the viewport; at
    gamma 1 Unreal's tonemapper writes linear values) and always keep a view state (without one Unreal skips every
    post-process material, so before #2396 the non-Lumen captures had no weather pass either).
- **Overcast, clouds, stars and the moon's phase (#2307).** The sky's overcast is the web's `day.overcast`:
  `max(Rain, 0.7 × Snow)` (`weather.js`: snow clouds are lighter). The clouds are `M_LundenClouds`, a copy of Epic's
  `m_SimpleVolumetricCloud` whose `Cloud_GlobalCoverage` parameter reads `MPC_LundenWeather` `CloudCoverage`, so the
  cover follows the weather at run time without a dynamic material instance (captures and tests call `UpdateSky` in an
  editor world). `UpdateSky` computes the web's sky cloud threshold (`cloudshadow.js` `skyCloudState`: `clearThr` over a
  clear sky, `thr[0]` → `thr[1]` with overcast, from the export's `site.sky.clouds`) as `CloudCover`, 0 clear … 1
  overcast, and maps it onto the material's coverage range `CLOUD_RANGE` (*guess* by eye: −1 for a clear sky, which
  leaves it empty as the web's 0.92 threshold does, to 1, a closed grey deck under rain; Epic's default is −0.2). The stars,
  the moon disc with its phase and the moon's halo are the web's sky shader (`daycycle.js` `skyFrag`) transcribed into
  `M_LundenPrecipitation`, drawn on sky pixels only, in the web's axes and in display units (× `EyeAdaptationInverse`,
  so they read the same at any exposure): stars on a 260-cell hash grid × `Night` (1 − daylight), faded towards the
  horizon; the disc `DAY.moonRadius` (0.04 rad, drawn ~9× the real moon as on the web) lit from the sun's side by the
  elongation (`MoonPh` = sin e, −cos e, lit fraction, from the same `moonState` terms) with the web's maria pattern and
  earthshine. The clouds hide them as the web mixes its clouds over them, by 0.85 × `CloudCover` (one value for the
  sky: the web hides a star behind each cloud, Unreal dims all stars by the cover; identical in clear weather and under
  rain or snow, the only weathers Unreal has). The moon light's own atmosphere disk is switched off.
- **Weather.** `Rain`, `Snow` (0–1), `Wet`, `WindSpeed` (m/s) and `WindFromDeg` (the direction the wind comes from,
  as Open-Meteo gives it; #2287 reads `WindSpeed`) are public variables; `ToggleRain` and `ToggleSnow` switch one on
  at full strength (and the other off) or off. Tick soaks `Wet` in about 10 minutes of rain and dries it in about 30
  (*guess*; the web integrates a film in `src/wetground.js`). `UpdateSky` copies the state to `MPC_LundenWeather`.

class; a non-actor (a subsystem, a widget) owns a small listener actor.

in UE 5.8.4, and the assets are rebuilt by script, never by hand. A Blueprint-declared event dispatcher can be created

none containing `OnStateChanged`, also after saving, with `declaring_class` and with a typed context pin) found the
same. Native dispatchers do appear (`…|CallOnX`, `…|AssignOnClicked`). A Blueprint interface gets further:
`BlueprintInterfaceFactory` creates `BPI_…`, `create_and_edit_function_graph` gives it a function with parameters, and
`add_call_function_node` places a call of it (pins `self`, `Id`, `IsOpen`); but its message node is not in the action
database, and neither `BlueprintEditorLibrary` nor `BlueprintGraphEditor` can add an interface to a listener Blueprint
(`ImplementedInterfaces` is not exposed to Python), so no listener could be built. A function on a Blueprint base
class can: #2312's probe built a base listener, a child that overrides the function with `add_function_override` and

## Build location (decision #2244)

**Decision (agent's recommendation, alternative 1; can be overturned in one sentence):** Unreal is built **locally
with scripts on the Windows development PC**; signing and publishing happen later in **GitHub Actions** (#2250).

- Why: GitHub-hosted Windows runners have 14 GB SSD — too little for the engine, project and Derived Data Cache.
  The repository is public, and a self-hosted runner on a public repository can be made to run code from other
  people's pull requests (booster-ai avoids it for the same reason). A cloud GPU VM costs money per hour and is not
  justified now.
- Security boundary: keep all signing keys and Azure credentials off the build PC. The local step retains the vendor signatures in the archive. A separate handoff to a draft release or artifact and signing/publication belong to #2248/#2250.
- Derived Data Cache: use the local Zen DDC on a fast disk outside the checkout. The default on Windows is
  `%LOCALAPPDATA%\UnrealEngine\Common\Zen\Data`. Set `UE-ZenDataPath` for a different local disk.
  [Epic documents the Zen data location and overrides](https://dev.epicgames.com/documentation/en-us/unreal-engine/using-zen-storage-server-as-cooked-output-store-for-unreal-engine).
- Another Windows PC can take over by following the install steps above, cloning the repository, running
  `git config lfs.fetchexclude ""` + `git lfs pull` and `check-environment.ps1`.

### Building a local Shipping archive

Use Windows Git to check out the intended commit with all Unreal LFS objects. Verify
`check-environment.ps1` on that checkout. From Windows PowerShell run

```powershell
.\tools\unreal-engine\release.ps1 -Version 0.1.0 -Content 12 -OutputRoot D:\LundenBuilds
```

`-Version` is the app version and `-Content` is its accompanying content version
(nonnegative integer). The default output root is `%LOCALAPPDATA%\Lunden\Builds`.
The script checks for staged, modified and untracked files and runs the import gate
([Automatic export and import](#automatic-export-and-import-2305); `-SyncImport` brings a stale import up to date
first) before calling
`RunUAT.bat BuildCookRun` for a Win64 Shipping cook, stage, IoStore package and
archive. It uses the installed target with `-nocompileuat -nocompile -skipbuild`
and omits the locally customized bootstrap with `-nobootstrapexe`. The MCP and
toolset plugins are enabled for Editor, and AndroidFileServer stays disabled in
Editor. Shipping uses the plugins compiled into Epic's stock UnrealGame.
Changing the runtime plugin set makes UAT generate a temporary native target.
The script checks HEAD and worktree cleanliness again after UAT. Each invocation
creates a separate directory under the output root containing `BuildCookRun.log`
and `archive/Windows/`. All invocations stage at the one fixed path
`<OutputRoot>\stage`, which the script empties before UAT; a named mutex lets only
one release build per PC run at a time (see [Pak repeatability](#pak-repeatability-2248)).
UAT can also use the engine's ordinary ignored
intermediate files in the project.

A completed archive contains the Shipping executable and `build-info.json` beside
the packaged `Lunden/` folder. The metadata contains `appVersion`, `contentVersion`,
the full Git `commit`, the actual `engineVersion`, the committed script blob ID
(`releaseScriptBlob`), completion time in UTC (`builtUtc`) and the verified
`runtime.path`, `runtime.sha256` and `runtime.publisher`. The archived
`Engine/Binaries/Win64/UnrealGame-Win64-Shipping.exe` must match the SHA-256
of the installed runtime and have a valid Epic Games Inc. Authenticode signature. A failed build
can leave files and its log in its own build directory. Hand off only a completed
archive. For #2248, build twice from one commit and compare the resulting program
and container files across the two archives.

**Verified end to end (#2244, 2026-11-20).** Two real `release.ps1` runs from the clean revision `c70a0bd2` in the
Windows clone (UE 5.8.4, content-only project) both exited 0 in 58 s and 31 s, each with its own build directory,
`BuildCookRun.log` and `build-info.json`. Both records hold the same `commit`, `engineVersion` 5.8.4,
`releaseScriptBlob` `d4164443` and runtime SHA-256 `E083AD2F…95953` (Epic Games Inc.); only `builtUtc` differs. Of the
26 archived files, 22 are byte-identical across the two runs, including every `.ucas`/`.utoc` container and all
executables. The other differences are `build-info.json` (time), UAT's two `Manifest_*UFSFiles_Win64.txt` (file
timestamps and order) and `Lunden-Windows.pak`. Extracting both paks with `UnrealPak -Extract` gives the same 1,730
files with identical SHA-256. The pak did not differ in entry order, as first assumed, but in its path-hash seed;
[Pak repeatability](#pak-repeatability-2248) has the cause and the fix.
With an untracked file in the checkout, the script stops with `Release requires a clean Git worktree` (exit 1) and
creates no build directory.

The Windows PowerShell execution policy on the build PC is unset (`Undefined` in every scope), which means the
Windows default `Restricted`. That refuses every `.ps1` started without an explicit policy. It is not Smart App
Control: the language mode is `FullLanguage`, and Code Integrity logged no script block. Start the scripts with
`powershell.exe -NoProfile -ExecutionPolicy Bypass -File …`. That applies to the one process only and changes no
machine or user policy.

runtime reads any value. Before the fix, `release.ps1` staged every build in its own GUID directory. The two

#### Sign a release manifest in Actions

The manifest key is an ECDSA P-256 pair (decision on #2248, 2026-11-20). The private key
was never written to disk. It exists only as the secret `LUNDEN_MANIFEST_PRIVATE_KEY` in
the protected `signing` environment, so it never reaches the build PC (#2244). The public
SPKI PEM is the repository variable `LUNDEN_MANIFEST_PUBLIC_KEY`. Launchers embed it, and
promotion verifies against it. A repository admin creates the pair once with
`tools/unreal-engine/create-manifest-key.sh`, which generates the key with `openssl` in shell memory and
pipes it straight into `gh secret set … --env signing`. Only the public key goes to `gh variable set`.
The script refuses if either value already exists. `--dry-run` checks access and
prints a throwaway public key without storing anything.

Upload `lunden-manifest-test.json` (or `lunden-manifest.json`) from `make-manifest.mjs` to the
versioned release, either as a draft or published without **Set as latest release**. Then run
**Sign an Unreal release manifest** ([workflow](../../.github/workflows/sign-manifest.yml)).
The `signing` environment only deploys from tags matching `v*`. A `workflow_dispatch` run
deploys from the ref it was started on, so the run must start from a `vMAJOR.MINOR.PATCH`
launcher tag whose commit contains the workflow. The release to sign is an input:

```sh
gh workflow run sign-manifest.yml --ref v0.2.1 -f tag=content-13 -f asset=lunden-manifest-test.json
```

The tag, release and asset names above are examples. Starting from a branch fails in the
unprivileged preflight job, before the environment is requested. Only tagged code ever sees
the key. The protected job has three steps:

1. `sign-manifest.mjs fetch`, with a token and no key, finds the single release with that tag
   (drafts included). It refuses the current latest release or an existing `.sig`, and
   downloads the manifest after checking its size and GitHub digest.
2. `sign-manifest.mjs sign`, with the key and no token, makes no network requests. It checks that
   the private key matches the public variable and signs the exact bytes as a 64-byte P1363
   signature. It keeps the signature only if the [verifier](../../tools/unreal-engine/verify-published.mjs)
   accepts it with the public key, schema and channel rules.
3. `sign-manifest.mjs upload`, with a token and no key, rechecks the release ID and the
   manifest asset (ID, size, digest and update time), verifies again and uploads
   `<asset>.sig`. It then downloads the uploaded asset and compares the bytes.

The workflow never changes latest. Promotion is still a separate step. The workflow
shares the promotion gate's concurrency group. To sign again, first delete the old `.sig`
asset deliberately. If the repository enables immutable releases, sign before publishing
the draft. Tests: `node --test tools/unreal-engine/tests/sign-manifest.test.mjs` (simulated
release API, throwaway in-memory keys) and `tools/unreal-engine/tests/create-manifest-key.test.mjs`
(fake `gh` on `PATH`; the private key reaches only its stdin). The Windows launcher test
workflow also runs `NodeSignedManifestTests`, so a Node-produced `.sig` must pass the C# reader.

**Rotation needs a launcher update.** Each launcher embeds the public key at build time and
accepts only manifests signed by that key, including the manifest that offers a launcher
self-update. `create-manifest-key.sh --rotate` replaces the secret and the variable together. The
old private key is gone, and promotion and the next launcher build immediately use the new
public key. Installed launchers then reject every new manifest. They must be reinstalled from a
new installer that embeds the new key. A transition without reinstalling would need one
last old-key manifest that delivers a launcher with the new key. The current tooling does
not support that, because it holds only one key. Treat a leaked private key as compromising
every installed launcher until users have replaced it.

### Publisher identity (#2277)

Azure Artifact Signing issues a new **leaf certificate every 72 hours**, and Microsoft rotates the
issuing CA as well. Pinning a leaf (the earlier `LUNDEN_SIGNER_SHA256`) would make every release
signed after the next rotation fail its own packaging check, and installed launchers would reject
the next update. The launcher therefore trusts the stable identity in the reviewed
[`unreal/Launcher/publisher-identity.json`](../../unreal/Launcher/publisher-identity.json), compiled in
as an embedded resource like the Unreal inventory. A file from the project is accepted only when:

1. Windows `WinVerifyTrust` (Authenticode policy, revocation checked except for the root) returns success;
2. the verified signature carries a timestamp countersignature (RFC 3161), which keeps it valid after the leaf expires;
3. the leaf's subject has exactly one CN equal to `commonName` and exactly one O equal to `organization`;
4. the leaf has the code-signing usage `1.3.6.1.5.5.7.3.3` and the certificate profile's durable identity usage `identityKeyUsage`;
5. the chain Windows built ends at the self-signed root whose certificate SHA-256 is `rootSha256`.

Intermediates are not pinned: they changed between two signings nine days apart. No leaf is pinned;
the protected build record only documents which leaf signed (`signer.leafCertificateSha256`).
`SignerIdentity.cs` implements the check, `Authenticode.cs` reads the chain and timestamp from the same
successful `WinVerifyTrust` call. Reviewed vendor images (below) still pin their exact leaf, because
their bytes, and therefore their signatures, never change.

`BoosterAI-Setup-*-win-x64.exe` (same Artifact Signing account and profile as Lunden, #2250). The

## Shared data: web → Unreal (#2245)

Web changes in ported groups are carried into Unreal under CLAUDE.md "Carry web changes into Unreal" (#2304); the
[inventory](unreal-inventory.md#keeping-unreal-in-step-with-the-web-2304) describes the procedure and the list of
affected Later groups. Changes that reach Unreal through this export only need the [staleness check](#staleness-check).

The web and Unreal versions are built from the same sources; nothing is modelled twice. The contract — what is
canonical where, formats, versions and ids — is [`shared/README.md`](../../shared/README.md) with JSON Schemas in
`shared/schema/`. `data/`, `models/`, `textures/` and `music/` stay where they are (the web's publishing relies on
those paths).

### Axes and units

Web/plan: metres, right-handed, x = east, y = up, z = south (north = −z) ([architecture](architecture.md#geometry-pipeline)).
Unreal: centimetres, left-handed, X forward, Y right, Z up. **Target mapping:** `Unreal X = 100·x`, `Unreal Y = 100·z`,
`Unreal Z = 100·y` (an axis swap, determinant −1: right-handed becomes left-handed without mirroring the plan; north is
Unreal −Y). Yaw: `unrealYaw = −90° − yawDeg` for `?at=`/`START` (web 0 north, 90 west, 180 south, −90 east, verified against
`src/player.js` `spawn`: `camera.rotation.y = yaw`, a camera looks down local −z); an object's `rotation.y` a
(radians) → `unrealYaw = 90° − a`; pitch unchanged. Implemented in `tools/unreal-engine/coordinates.mjs`;
`node tools/unreal-engine/coordinatestest.mjs` checks L1007's four outer corners (`data/plan.json`), the stair foot, START at eye
height and Övre plan's floor within 1 cm, a north arrow → Unreal −Y, and the yaw formula against the camera's real view
direction for 97 yaws. **Verified in phase B (5.8.4):** Interchange's glTF translator converts glTF (metres, +Y up,
the web's axes) into exactly this mapping (`X = 100·x`, `Y = 100·z`, `Z = 100·y`): all seven fixture points and both
arrow tips land with 0.000 cm error and the north arrow points to Unreal −Y. Neither the exporter nor the importer
applies an axis correction, so there is no second place to keep in step.

### Export

```text
PLAYWRIGHT_MODULE=/path/to/node_modules/playwright tools/browsertest.sh node tools/unreal-engine/export-world.mjs [--out DIR] [--zones l1007,l1007-uteplats,fixture]
```

(On Windows without WSL: `node tools/unreal-engine/export-world.mjs` with Playwright installed; `browsertest.sh` only adds the
shared memory ceiling and browser slots of the WSL agent machine.) The driver serves the repository on a private
127.0.0.1 port, opens `tools/unreal-engine/export.html` in headless Chromium and runs `tools/unreal-engine/export-scene.js`, which calls the
real `buildWorld(plan)` plus `src/lights.js` (ceiling lamps, pendants, switches) — no renderer, no `main.js`, so no
detail culling, phone LOD proxies or quality tiers. The world's own static bake (`mergeStatic` with a cell function in
`src/world.js`: one mesh per material and level) is skipped by serving `src/merge.js` wrapped for the export page only;
doors, furniture pieces and small models keep their per-object merge. **Nothing in `src/` changes and no URL parameter
was added** — the published site and players are unaffected (tools/ is not published; `stamp.sh`'s `CONTENT` hash
does not cover `tools/unreal-engine/`, `shared/` or `unreal/`). Pages ignores pushes that only touch `unreal/**`,
`tools/unreal-engine/**`, `shared/schema/**` or `*.md` (`paths-ignore` in `pages.yml`, kept by #2243).

What is exported:

- **Zones** (a node belongs to the first zone whose box holds the centre of its world bounding box and whose `from`
  accepts the builder it comes from): `l1007` (L1007's two floors: walls, structure, doors, windows,

  plates; since #2310 also the fruit bowl and Tilly's basketball, see below), `l1007-uteplats` (patio paving, fences, hedge, patio furniture), `fixture` (the position test), and since
  #2279 the buildings round L1007: `l1007-entre` (the street, pavement and terrain in front of L1007 up to START),

  See [Buildings](#buildings-hus-l-hus-abc-and-the-garage-2279).
- **Patio parasol and string lights (#2373).** The parasol already belongs to the furniture list. The export applies
  the web's clear daytime canopy pose after assigning its stable furniture ID. The fence strings come from
  `buildStringLights` with the same plan fences as the game. Their cable, bulbs and the two pools of light are in
  the patio export and lighting measurements. On import, each bulb receives the `patio:string-bulb` tag. The first
  string light creates a shared unlit material instance on the bulbs and sets its base colour from the same dusk
  fade that drives the point lights. Both pools read raw daylight at the fence string’s exported on/off thresholds.
  The weather collection exposes the sky’s raw `Daylight`, decimal `Hour`, and the external `PowerAvailable` factor
  (1 at startup). A power change scales both point lights and bulb glow while preserving the dusk state.
  Other automatic lamps use cloud-adjusted daylight. The static canopy represents the export date. Reacting to later
  changes of sun, season or manual folding in the Windows game requires runtime interaction.
- **Fruit bowl and basketball (#2310).** `main.js` builds them next to the world, so `export-scene.js` constructs the
  same classes with main.js's arguments (`new FruitBowl(scene, camera)` from `src/fruit.js`; `new Basketball(scene,
  camera, { world })` from `src/basket.js`, without the bullet marks and the outdoor hoop, which only matter in play)
  after every other builder, so the seeded random sequence of the other zones is unchanged. Three `furniture` nodes in
  `l1007`: `furn_fruitbowl_l0_x332_z1052` (`source` `src/config.js#FRUIT`, name `fruktskålen`; the copper wires and the
  nine pieces of fruit are its parts), `furn_basketholder_l1_x31_z1108` (`webId` `f-basketholder-1-0.2-0-0` from
  `Basketball.holderMovable()`, the same entry main.js adds to `world.furniture.movable`) and `furn_basketball_l1_x33_z1108`
  (the ball is its own node, although the web hangs it in the holder; `src/config.js#BASKET.ball`). The default state:
  every piece in the bowl, the ball at home. The two modules bring `src/stats.js`, `src/keep.js` and their score
  modules into the [source list](#staleness-check), so a change there also makes the export stale.
- **Nodes** carry `extras` (`shared/schema/node-extras.schema.json`): stable `id` (= node name; kind + level +
  position in cm), `kind` (`wall | structure | door | window | furniture | interactive | light | collision | fixture |
  part`), `zone`, `level`, `source` (a pointer such as `data/plan.json#/floors/0/doors/0` or
  `src/config.js#FURNITURE[12]`), the web's display `name`, `webId` (furniture's saved-layout id) and `materialKeys`.
  Walls are recognised as the plan's wall polygons; other static building geometry is `structure`.
- **Mesh names:** `export-world.mjs` names every glTF mesh after the first node that uses it and the glTF scene
  `<zone>__scene` (GLTFExporter leaves them unnamed; Interchange would then name assets `<zone>_mesh_<index>`, so one
  added node renamed every later asset). Only the GLB's JSON chunk changes; still deterministic.
- **Materials** are not the web's: canvas textures (except the furnishing images, [#2289](#furnishing-and-pictures-2289)) and `onBeforeCompile` shader tweaks do not travel. Each mesh gets a
  plain PBR material named by a key built from its look (`std_f1f1ee_r85_m0` = standard, colour f1f1ee, roughness
  0.85, metalness 0; suffixes for opacity, emissive, vertex colours, textures, double-sided). `measurements.json`
  `materials` lists every key; Unreal maps keys to hand-made materials (#2246). One key can stand for several web
  materials (the key leaves the colour map out), so each entry also lists its `looks` (#2318): the web's own surface
  class (`surface`: the weather layers' tag, `userData.wetSurface`/`wetGround`/`snowGround`, e.g. `brick`, `roof`,
  `asphalt`, `paving`), the colour map's name (`map`) and its first-use order in the export (`mapIndex`; canvas maps
  have no name, so an untagged material drawing a tagged one's canvas is recognised by it). A key with more than one
  look lists the node ids showing each (`nodes`). The GLBs do not change; only `measurements.json` does.
- **Left out** (web-only look, not geometry): `wall-ao`, contact shadows, architecture edge lines, glows/halos
  (non-normal blending), invisible pick/surface helpers, lights, hidden objects, instances scaled to zero (the web's way
  of hiding an instance, e.g. seven boule balls; their matrix has no rotation and wrote `null` quaternions). Instanced meshes become one node per
  instance. Seasonal pieces (the Christmas tree) are exported with `extras.seasonal`.
- **`measurements.json`** (`shared/schema/measurements.schema.json`): levels (FFL, RH, next floor, Unreal Z), START
  (feet/eye, Unreal location/yaw/pitch), player sizes and speeds, stair (foot, rise, riser, treads, opening), every door
  (swing: hinge, width, closed/open angle as web radians and Unreal yaw; sliding/wardrobe: centre and size), windows (plan
  rectangle, sill, head, transom, opening sash ids), lights (world lamps and the rooms' ceiling/pendant light points, each with a stable id since #2283),
  the terrain grid reference (`data/elevation.json` origin/step/size/hash and licence), site geo anchor and plan
  north (`site.sky`: the web's sky observer, light and weather numbers, #2283), material keys, and the fixture's expected positions. Points carry `web` (m) and `unreal` (cm).
- **`export-manifest.json`**: `formatVersion`, source commit (+ dirty flag), SHA-256 per file, and every source file
  with its hash.

Determinism: Date is fixed (2026-06-15 12:00 UTC: summer, no Christmas), `Math.random` is seeded (mulberry32, 2245),
three.js is served from `node_modules/three` when it is the pinned 0.170.0 (else the CDN), the build and the
collection run synchronously before any later load, and nothing time-dependent is written. Two runs from the same
commit give byte-identical files. Size (2026-11-20): `l1007.glb` ≈ 81 MB, 2,614 nodes, ≈ 881k triangles (the
furniture is detailed; the ZZ plant alone is 62k), `l1007-uteplats.glb` ≈ 7.5 MB, `fixture.glb` 12 kB; a run takes
about 25 s and peaks near 2.8 GB of browser memory.

(`unreal/Lunden/Import/` is ignored). The imported assets are not versioned either: see
[Generated assets](#generated-assets-rebuilt-not-versioned-decided).

### Staleness check

`node tools/unreal-engine/check-export.mjs [--dir DIR] [--allow-missing]` — no Unreal, no browser. It recomputes the source list
(`tools/unreal-engine/sources.mjs`: the import closure of `tools/unreal-engine/export-scene.js` and `src/lights.js`, `data/plan.json`,
`data/elevation.json`, `models/*.glb` and the exporter itself) and compares it with the manifest, verifies each
file's SHA-256, and validates the manifest, `measurements.json` and every GLB node's extras against `shared/schema/`.
Exit 0 current, 1 **STALE** (lists the changed sources: export and import again), 2 no export (0 with
`--allow-missing`), 3 invalid (unknown `formatVersion`, schema error, edited or missing file). It is not wired into the
Pages workflow (no export exists there); the Unreal export workflow and the release gate run it
([Automatic export and import](#automatic-export-and-import-2305)).

### Automatic export and import (#2305)

Web changes reach the Unreal import without anyone running the export and import by hand, in two halves.

**Export in GitHub Actions** (`.github/workflows/unreal-export.yml`, Linux). Every push to `main` checks the versioned
Lighting against its export. A manual run (`workflow_dispatch`, `force`) can also re-export the scene.

1. the tool tests (`tools/unreal-engine/tests/export-ci.test.mjs`, `check-import.test.mjs`);
2. the export key: `node tools/unreal-engine/export-ci.mjs key` = the source hash of `sources.mjs`. An unexpired artifact
   `unreal-export-<first 16 hex>` means these sources were already exported. The workflow reuses its measurements
   and skips Chromium, the zone comparison and the full export upload;
3. otherwise Playwright 1.58.2 (browser cached) and three 0.170.0 are installed without a lockfile (on `ubuntu-24.04`:
   1.58.2 has no Chromium for `ubuntu-latest`'s Ubuntu 26.04, which failed the first run, #2316), then
   `export-world.mjs`, `check-export.mjs` and `export-ci.mjs compare` against the previous run's
   `unreal-export-manifest` artifact: a zone table (unchanged / changed / new / gone, nodes, triangles, SHA-256) and the
   changed sources in the run summary;
4. uploads the export as `unreal-export-<hash>` (30 days; about 185 MB uncompressed) and the manifest plus
   `export-diff.json` as `unreal-export-manifest` (90 days, the next run's baseline);
5. reads the real `Lunden.SpecHash` metadata on the committed LFS asset `BP_LundenSky` and compares it with
   `build_lighting.py`'s signature of the current measurements and builder sources (#2385). This runs on fresh exports,
   cached exports and pushes that only change a Blueprint or Python file. The small measurements cache is keyed by the
   full export source hash. A cold cache reads `measurements.json` from the matching full artifact. The workflow
   uploads newly exported inputs before this check, so they are available for a Windows rebuild on a failed run;
6. `export-ci.mjs report` keeps **one tracking issue** (marker `<!-- unreal-export-ci -->`, `bug`, `priority: medium`,
   title `Bugg: Unreal-exporten i Actions misslyckas eller avviker`). A failed step or a deviation opens it, or comments
   on it while it is open; the first green run afterwards notes that once. Closing it stays with whoever fixes the
   cause. Deviations: a zone no longer exported, a zone's nodes or triangles at 0 or below half of the previous export
   (`SHRINK_LIMIT`, a *guess*), or other bytes from the same source hash (a forced re-export that is not deterministic).
   A zone that merely changed is the normal case and only appears in the summary. `--dry-run` prints the `gh`
   commands instead of running them.

The Pages workflow is unchanged; this workflow only reads the repository, uploads artifacts and writes that one issue.
Run the same Lighting check locally in WSL from the repository root after exporting or downloading the current scene:

```sh
git lfs pull --include='unreal/Lunden/Content/Lunden/Lighting/BP_LundenSky.uasset' --exclude=''
python3 tools/unreal-engine/check-lighting.py unreal/Lunden/Import/measurements.json
```

WSL can also pass `--sky-asset /path/to/BP_LundenSky.uasset` to read a hydrated copy from another checkout. It must
match this checkout's LFS object. On a stale signature, the Windows Lighting owner takes the LFS locks, runs
`tools/unreal-engine/run-python.ps1 tools/unreal-engine/python/build_lighting.py <path-to-measurements.json>`
and commits the resulting changes under `unreal/Lunden/Content/Lunden/Lighting`. The generated level's local
`build-stamp.json` is not a substitute for the Blueprint's tag.

**One producer per PC.** The same sources give the same nodes, triangles and `measurements.json` on every machine,
but zones with canvas-drawn pictures (signs, name plate: `l1007`, `hus-l`, `kvarteret`) differ in their embedded image
bytes between the workflow's Linux runner and a WSL or Windows export (fonts and browser build; first comparison on
`9951f5be…`, 2026-11-21). Switching between a workflow artifact and a local export therefore re-imports those zones once;
nothing is wrong, but prefer one producer (the artifact) on a PC.

**Source hashes ignore line endings (#2305).** `sources.mjs` hashes text sources (`.js`, `.mjs`, `.json`, `.html`) with
CRLF read as LF, so an export made on Linux, in WSL or by the workflow counts as current in the Windows clone, whose
Git checks text out with CRLF (`core.autocrlf=true`). Binary sources (`models/*.glb`, pictures) are hashed as they are.

**Import on the Windows PC** (`tools/unreal-engine/sync-import.ps1`, headless, no window):

```text
powershell.exe -NoProfile -ExecutionPolicy Bypass -File tools\unreal-engine\sync-import.ps1 [-ExportFrom <dir>] [-ImportOnly] [-Zones a,b] [-DryRun]
```

1. keeps `unreal/Lunden/Import/` when `check-export.mjs` says it is current; otherwise takes `-ExportFrom <dir>`, the
   workflow's artifact for this source hash (needs an authenticated `gh`: `winget install GitHub.cli`, `gh auth login`),
   or a local export (needs Playwright in the checkout: `npm install --no-save playwright@1.58.2 three@0.170.0` and
   `npx playwright install chromium`), and checks it before it replaces `Import/`. With none of these it stops and
   names all three;
2. `build_seasons.py`, then `import_world.py`. The season assets come first because the river, lawn and leaf
   materials read `MPC_LundenVegetation` (#2380); the step saves nothing while the committed `MPC_LundenVegetation`
   and `BPC_LundenSeasons` match the script. Zones whose GLB is unchanged are skipped by their import stamps, so only
   changed zones cost import time;
3. the derived levels in build order, each skipping itself when its inputs are unchanged: `build_l1007.py`,
   `build_exterior.py`, `build_site.py`, `build_lighting.py`, `build_vegetation.py`, `build_interaction.py`;
4. `compose_world.py --check` (never saves the map; a moved START needs the map owner's locked run);
5. `import_world.py --check` as the quick test (stamps, content fingerprints, ids, collision, fixture positions);
6. writes `Generated/sync-stamp.json` (export manifest hash, steps, builder-script hash) and runs the release gate.

Any failing step stops with exit 1 and its name; each Unreal step's log is under `unreal/Lunden/Saved/Logs`. A builder
that has to save a versioned asset (for example `BP_LundenSky` when the lamps changed) needs its LFS lock and leaves
the worktree changed; commit it before a release. `-ImportOnly`/`-Zones` run steps 1, 2 and 5 only and mark the sync

### Import into Unreal (verified 2026-11-20)

```text
powershell.exe -NoProfile -ExecutionPolicy Bypass -File tools/unreal-engine/run-python.ps1 tools/unreal-engine/python/import_world.py [<export dir>] [--zones l1007,fixture] [--force] [--measure <id>,…]
powershell.exe -NoProfile -ExecutionPolicy Bypass -File tools/unreal-engine/run-python.ps1 tools/unreal-engine/python/import_world.py --check [--measure <id>,…]
powershell.exe -NoProfile -ExecutionPolicy Bypass -File tools/unreal-engine/run-python.ps1 tools/unreal-engine/python/build_materials.py [--force | --check]
```

Run in the Windows clone after copying (or writing) the export to `unreal/Lunden/Import/`. Every run reads the
manifest (refusing a newer `formatVersion` or a changed file), imports or skips each zone, then loads each zone level
and checks it: ids, the fixture (zone `fixture`) and, with `--check`, the stamp and content fingerprint without
importing. It ends with `LUNDEN_IMPORT_OK` / `LUNDEN_CHECK_OK`; any failure raises, so `run-python.ps1` exits 1. This
`--check` run is the headless position test (no C++ Automation Test: the project becomes content-only, #2268).
`--measure` logs the world bounds of named objects (`LUNDEN_IMPORT_MEASURE`), for round-trip checks.
Run `build_materials.py` before an import when `material-map.json` changed (see [Surface materials](#surface-materials-2282)).

What 5.8.4 does, and what the importer does about it:

- **Scene import, not asset import.** `.glb` goes through Interchange's glTF translator either way. An
  `AssetImportTask` creates static meshes only, with node transforms **baked into the vertices** (every pivot at the
  world origin) and no actors. The importer uses `InterchangeManager.import_scene` with the project's default glTF
  scene stack (`DefaultGLTFSceneAssetsPipeline`, `DefaultGLTFPipeline`, `DefaultSceneLevelPipeline`) into a blank
  map: one actor per glTF node with its transform and attachment (a door's actor pivots at its hinge), StaticMeshes in
  local space under `<zone>/StaticMeshes/`, one MaterialInstanceConstant per material key under `<zone>/Materials/`
  and an `InterchangeSceneImportAsset`. The map is saved as `/Game/Lunden/Generated/<zone>/Level_<zone>` (a plain
  level, not World Partition: generated, one owner). Shared glTF meshes stay one shared asset.
- **Names and tags.** Interchange names actors `<zone>_node_<index>` and labels them with the node name; the importer
  renames each actor object to its id and keeps the id as label. Interchange stores node extras only as asset
  metadata on a StaticMesh (`INTERCHANGE.<node>.id` …, `EditorAssetLibrary.get_metadata_tag_values`), for the first
  node of a shared mesh, never on actors. The importer therefore reads the extras from the GLB and writes actor tags
  `[<id>, kind:<kind>, zone:<zone>, level:<n>, webId:<id>, source:<pointer>, parent:<id>]` (absent values left out).
  A node with `seasonal` extras and all its parts also get `seasonal`, `season:<what>`, `seasonFrom:<MMDD>` and
  `seasonTo:<MMDD>` (importer version 3; [Seasons](#seasons-2295)).
  Tags and object names survive packaging (labels are editor-only); Blueprints find objects with *Get All Actors
  With Tag* on the id.
- **Collision.** `collision` nodes (the web's wall rectangles and floor plates, one shared unit cube) get a single
  simple box on the cube mesh, `BlockAll`, hidden in game (54 in l1007). `get_editor_subsystem(StaticMeshEditorSubsystem)`
  is `None` in the commandlet, and the deprecated `EditorStaticMeshLibrary` there **silently does nothing**: until
  importer version 4 the cube had no box at all, at import or after a restart (#2297; the empty shape set seen in
  [the #2246 route](../verification/2246/route.md)). The importer therefore uses a new `StaticMeshEditorSubsystem`
  instance (`static_mesh_editor()` in `prepare_nanite_materials.py`), and the import and `--check` fail unless every
  collision actor is a hidden `BlockAll` mesh with one simple box (`LUNDEN_IMPORT_COLLISION`). Visible meshes keep
  Interchange's default collision (no simple shapes, so the player's capsule passes them; what the player collides
  with is the derived collision levels). Interchange leaves their complex collision **single-sided**: a trace from
  behind a face went through it (the A/B entrance glass, #2299). Since importer version 6 every imported mesh's
  `BodySetup` has `double_sided_geometry` on, saved with the mesh; the import and `--check` fail on a single-sided mesh
  (`LUNDEN_IMPORT_DOUBLE_SIDED`). The fingerprint does not cover the flag, so version 6 left every zone's fingerprint
  unchanged and derived builds that record it keep skipping. Measured on all nine zones (export of 66b1b6fb): 3,490
  meshes, package bytes +0.05 % (hus-l 119.77 → 119.83 MB), import not slower (l1007 59 s, hus-l 23 s with a warm DDC)
  ([#2299 verification](../verification/2299/README.md)).
- **Materials.** `tools/unreal-engine/material-map.json` rules (a regex on the key, first match wins, optionally
  narrowed by a `mesh` regex on the StaticMesh name) replace the imported instances on the mesh slots by hand-made
  materials ([Surface materials](#surface-materials-2282)). Other keys keep Interchange's glTF material instance
  (colour, roughness, metalness, opacity and emissive from the export); a vertex-coloured key's instance is then
  re-parented onto a master that draws the vertex colour ([Vertex colours](#vertex-colours-2321)).
- **Clearing a zone.** `EditorAssetLibrary.delete_directory` left the `.umap` behind, logged *Error opening file* for
  every package and was still working after 7 minutes on l1007's 2,426 assets (killed). `Generated/<zone>/` belongs to
  the importer alone, so it removes the folder on disk and rescans the asset registry when none of its packages is
  loaded (else the editor deletion). `LevelEditorSubsystem.new_level` saves an empty level at once and then refuses
  the path after a failed import, so the importer builds in a blank map and saves it with `save_map` at the end.

**Nanite materials in cooked builds (#2276).** The importer reads each mesh slot's
effective blend mode, including overrides on glTF instances. Any translucent or
otherwise unsupported slot sends that mesh through the regular raster path.
Opaque and masked Nanite meshes use a saved Nanite usage flag on project materials
and an explicit override on imported material instances. Interchange's engine
material stays shared. Importer version 2 regenerates older stamped zones.
The raster switch goes through `StaticMeshEditorSubsystem.set_nanite_settings(mesh, settings, True)`, which rebuilds the
render data at once. Setting `nanite_settings` with `set_editor_property` only flips the flag (measured in the
commandlet, #2297): the session keeps the Nanite fallback mesh until the next editor start, so `get_num_vertices`/
`get_num_triangles` and anything else that reads the render data see the reduced mesh (on l1007, 34 of the 73 raster
furniture meshes, e.g. 370 instead of 992 triangles). The import then stamped a fingerprint that no fresh editor
reproduced. Since #2298 the builders' copies (`build_exterior.py`, `build_site.py`, `build_vegetation.py`) and the
capture scripts' in-memory switch use `set_nanite_settings` too.

**Idempotency, defined.** `Generated/<zone>/import-stamp.json` records the GLB's SHA-256 and source commit, the
importer version, the engine version, the hash of `material-map.json`, a content fingerprint and the SHA-256 of every
package file. When all of these match and every package file is byte-identical, the zone is **skipped and nothing is
written**; the check for "a second import changes no asset" is a byte comparison of every file under `Generated/`
before and after the run. A changed export, importer version, engine or material map, and any edited or missing
package file (a hand edit), re-imports the zone. A *forced* re-import (`--force`) is never byte-identical: every new
package gets a new persistent GUID (2,501 of 2,501 files differed). Its check is the **content fingerprint**, a SHA-256
over every actor (name, label, class, parent, transform to 0.01, tags, mesh, collision profile, hidden flag) and every
asset (class; for meshes vertices, triangles, bounds to 0.01, slot materials and simple boxes). The import computes
it after the save, and `--check` recomputes it in a new editor process; importer version 4 (#2297) made the two agree
for zones with raster meshes. Version 4 changes the fingerprint only where a mesh left Nanite with a reduced fallback
or a zone has collision nodes: l1007 changed, `fixture` (`70a3715f2b59d0eb`) and `l1007-uteplats`
(`88dbd0aee8ee6a16`, export of e8e7e288) did not, so derived builds that record them stay current; results in
[the #2297 verification](../verification/2297/README.md). Version 5 (#2298) changes the fingerprint of every zone
whose Nanite fallback was reduced (all but `fixture` and `l1007-entre`), so the derived builds rebuild once.

### Surface materials (#2282)

The export's keys describe a look (`std_<colour>_r<roughness>_m<metalness>` plus suffixes), not a surface, and its
canvas textures do not travel. `tools/unreal-engine/material-map.json` therefore holds three lists:

- `materials`: every hand-made asset in `/Game/Lunden/Materials/`. Three masters cover the building and ground
  surfaces: `M_LundenSurface` (plain opaque PBR), `M_LundenTiled` (tiles, slabs, planks, boards, bricks and fine
  aggregate drawn by one Custom HLSL node in the export's metre UVs) and `M_LundenGlass` (translucent glazing, so its
  meshes use the raster path, #2276). Since #2308 `M_LundenGrass` draws the lawns (see [Vegetation](#vegetation-trees-shrubs-and-hedges-2281)). The `MI_Lunden*` instances take their sizes and colours from the web's
  `COLORS`, `FINISH`, `PATIO.paving` and `SCREEN_WALL`. `MI_LundenFacadeBrick`, `MI_LundenAsphalt` and
  `MI_LundenRoofSeam` were prepared for the exterior and ground zones and are wired since #2318 (see below).
  Each entry names its web `source` and an `assumption`; `build_materials.py` writes both into the asset metadata
  (`Lunden.Source`, `Lunden.Assumption`), so plan-material's *guess* markers stay with the material.
- `rules`: key → material. The tile key `std_ffffff_r100_m0_tex` is shared by the hall and wet-room floors, the wall
  tiles, the splashback, the patio paving and the screen walls, so its rules add a `mesh` selector (the StaticMesh
  name is the id of the first export node that uses it). The last rule for that key has no selector and catches any
  other surface with white wall tiles.
- `defaults`: keys left on Interchange's instance, each with a reason (plain opaque fittings, transparent and
  emissive fittings, textured fittings that belong to furnishing #2289, grass for #2281).

`scope` lists the zones and node kinds whose keys count as building and ground surfaces. Before an import, after the
export, run the coverage check (no Unreal needed):

```text
python3 tools/unreal-engine/tests/test_materials.py [<export dir>] [--table]
```

It fails when a key on those nodes has neither a rule nor a default, a rule names an unlisted material, a `mesh`
selector selects nothing (a moved surface changes its id), an instance names an unknown parameter, or an entry that
says *guess* has no assumption. `build_materials.py` skips an asset whose `Lunden.SpecHash` matches its entry, so a
second run writes nothing; `--force` rebuilds in place and `--check` verifies existence, spec hash, metadata,
parameters and the persisted Nanite usage without writing. Take `git lfs lock` on every `Materials/*.uasset` before a
build that writes. Results are in [the #2282 verification](../verification/2282/README.md).

**Collection GUIDs (#2408).** A `CollectionParameter` expression stores its parameter's GUID and looks the name up
through it when it loads. A collection rebuilt with new parameter structs leaves its readers pointing at nothing. Before
#2381 kept the structs, `MPC_LundenWeather` got new ones on every rebuild. The expression then loads as parameter
`None`, and the material either fails to compile or reads 0:
- the river rendered the default grey (#2408);
- the foliage wind read 0 (#2383).

### Vertex colours (#2321)

Many web materials take their colour from the mesh's vertex colours (`vertexColors: true` on a white or light base
colour): the sill and pot plants' leaves and flowers, the fruit, the river bridges' railings (`src/riverbridge.js`), the
vents, the Weber grill, the Christmas tree, the core stairwells' walls, the door fittings' key slots. The door handles
themselves are brushed steel (`src/doorfittings.js`: `0xc9cdd0`, metalness 0.72, vertex colour 1): they look black on
the web at night only because the web's metals reflect no environment; Unreal's are steel-grey, unchanged by #2321. The
export keeps the colour attribute (`COLOR_0`) and marks the key `_vc`, and Interchange imports the colours onto the
StaticMesh, but its glTF masters (`/InterchangeAssets/gltf/M_Default`, `M_Unlit`; probed on 5.8.4) multiply them only
in `MF_BaseColor`'s base-colour-texture branch (static switch `bHasBaseColorTexture`, on for the furnishing images of
#2289). Every other vertex-coloured key rendered as its plain base colour, so the plants, fruit and railings were
white. Keys whose colour sits in the base colour (Hus L's entrance plants in `exterior.js`, `std_3f7a3a_r80_m0_ds`, and
the hedges, `std_78a64b_…`) were unaffected, which is why they were green.

- **Masters.** `build_materials.py` builds `M_LundenGltfVertexColor` and `M_LundenGltfUnlitVertexColor` (graph
  `gltf-vertex-color`): a duplicate of Interchange's master (`from`) whose `BaseColor` (unlit: `EmissiveColor`) output
  goes through one Multiply with `VertexColor`, with the Nanite usage flag. A copy keeps every parameter name, so an
  imported instance keeps its values on it. Its spec hash includes the engine version, so an engine update rebuilds it
  from the new engine master. `--check` also fails when the output is not multiplied by the vertex colour.
- **Import.** After the rules, `import_world.py` re-parents every imported instance of the zone whose key matches
  `material-map.json` `vertexColor.match` (`_vc`) and whose `bHasBaseColorTexture` is off from its Interchange parent
  (`MI_Default_Opaque`, `…_DS`, …) onto the copy of its master listed in `vertexColor.masters`, and copies the parent
  chain's blend, two-sided and mask overrides onto the instance itself (the asset name, the key, is unchanged). An
  unlisted master fails the import, and `--check` fails on an untextured vertex-coloured instance on a master without
  vertex colour (`LUNDEN_IMPORT_VERTEX_COLOR`). Textured ones stay on Interchange's master: a copy would multiply them
  twice. The map's hash changes with the section, so every stamped zone is imported again; the importer version is
  unchanged.
- **Coverage.** `tests/test_materials.py` reads every zone's GLB: each key with vertex colours (`_vc` or `COLOR_0`)
  must get a rule's material that multiplies the vertex colour in (a `gltf-vertex-color` master, or a grass instance
  with `VertexColorWeight` above 0), have a base colour texture in the GLB, or match `vertexColor.match` with the glTF
  master Interchange gives it (by the material's extensions: unlit, transmission, clearcoat, sheen, else `M_Default`)
  listed in `vertexColor.masters`. The export of `816b695d` has 56 such keys in 7 zones (64 zone instances, 6 of them
  textured), all on `M_Default` (the web's `MeshBasicMaterial` keys export without `KHR_materials_unlit` and import lit).
- Hand-made materials of the rules ignore the vertex colour unless their master reads it; the lawns' grass master has
  `VertexColorWeight` 0 and no lawn key is vertex-coloured. The vegetation's leaf cards keep `MI_LundenLeaf` (#2281),
  which multiplies the vertex AO. Textured keys with vertex colours (`…_vc_tex_t…`: the sofas' upholstery, the garage
  signs) keep Interchange's textured branch, which already multiplied them; their darkness is #2322. Results:
  [the #2321 verification](../verification/2321/README.md).

since #2302.

**Control points and route.** `groundProbes` in `export-scene.js` defines ten `elevation` points, on terrain-mesh

bounds against its visible actor, and walks the route START → street → ramp → courtyard → back → Sankt Lars väg → park
level → shore path → Höje å valley, each checkpoint within 20 cm of the web's surface. The drawn terrain lies 1 cm under

### Vegetation: trees, shrubs and hedges (#2281)

**Zone.** `vegetation` (last in `zoneTable`, so every earlier GLB stays byte-identical) takes, with `only: VEGETATION`,
what #2280's `SITE_SKIP` leaves out as vegetation: the site's `tree-trunks|birches|crowns <cell>` InstancedMeshes (one
node per trunk and per crown lobe), the river park's understory and the pavement shrubs (lobes in the same batches), the
courtyard plantings and pergola vines, the river bank's growth and the entrance boxwood. Never the web's `… far` LOD
stand-ins, the backdrop's woodland, fallen leaves or furniture. Hus L's patio hedges and the entrance plants stay in
`hus-l`, L1007's own patio hedge in `l1007-uteplats`. At `3c071946`: 4,164 nodes, 341,074 triangles, 2.5 MB, six
shared meshes (crown lobe 3,129 instances, trunk 812, birch trunk 15, courtyard lobe 205, shore growth 1, boxwood 1).

**Measurements.** `measurements.json` `vegetation` (`export-scene.js vegetationData`) lists every exported tree: a
foot of `src/surroundings.js` `treeFeet` whose trunk instance is exported (507: all of them), with its crown radius
(`aoTrees`), its lobes (each lobe goes to the tree whose foot is horizontally nearest in crown radii, within 1.5), its
height (the highest top of the trunk's and its lobes' boxes above the foot) and `heightClass = round(height / 2 m)`;
and every hedge in any zone (`patio-hedge`/`boxwood` by object or material name; 9: Hus L's seven, L1007's, the
boxwood) with box centre, size and `heightClass = round(height / 0.25 m)`. `look` carries the leaf material keys,
the twelve crown colour and cover rows from `SEASON.trees`, the blossom months, and wind settings from
`SITE_WIND` and `WIND.power`. The GLB embeds the ordinary and birch bark colour and roughness textures, with
the web's UV repeat. Interchange keeps these materials on the generated trunks.

**Builder.** Run `build_seasons.py` and import the `vegetation` and `l1007-uteplats` zones before `build_vegetation.py`.

- `M_LundenFoliage` reads the month that `BPC_LundenSeasons.ApplySeason` publishes to `MPC_LundenVegetation`.
  `MI_LundenLeaf` gives deciduous crowns the month's colour and cover, with per-instance variation. A zero-cover
  month masks the whole crown, including its opaque core. `MI_LundenPerennial` keeps the courtyard shrubs green
  throughout the year. The leaf-card cut-out, colour variation and sway amplitude are visual calibration (*guess*).
- The foliage master reads `WindX` and `WindY` from `MPC_LundenWeather`. The downwind vector in m/s drives the
  web's wind-power curve, gust envelope and flutter, with the offset capped at `maxDisplacement`. The builder
  records the GUIDs of both wind parameters and `Month` in `Lunden.SpecHash`. If a collection changes those GUIDs,
  the check reports a stale master and the builder reconnects it. [Wind binding verification](../verification/2383/README.md).
- `Generated/VegetationWorld/` contains the generated mesh copies, foliage types and `Level_vegetation_foliage`.
  Nanite is disabled on the copies (#2298). The foliage type enables world-position offset on crowns and the 12
  evergreen courtyard perennials. Pergola vines retain their seasonal colour and stay still. The level includes a
  tagged copy of each hedge whose source zone is absent from `world-levels.json` (L1007's patio hedge).
  `vegetation-index.json` records the source, role, leaf slots and instance count for each mesh.
- **Trunk collision (#2308).** The web stops the walker at a trunk only outside the home block (`src/farwalk.js`: a
  diamond of half-width `WALK.trunk[kind]`, big 0.45, tree 0.3, birch 0.2, young 0.15 m, *guess* in the web; trunks
  inside `OUTDOOR` do not block). The export writes that rule (`vegetation.trunkCollision`) and each tree's half-width
  or null (`trees[].blocks`); the builder puts a hidden `BlockAll` engine cube on every blocking foot, turned 45° so its
  corners are the diamond's, up to the tree's height (448 of 507 trees at 8750af3c; tagged `derived:trunk-collision`,
  `tree:<id>`). `test_vegetation.py` checks every cube against the export and walks the character diagonally at a
  sample of trunks (the first blocking trunk of each kind and two home-block trunks).
- The builder regenerates this level from the import under `Generated/VegetationWorld/`. The three assets under
  `/Game/Lunden/Vegetation/` are versioned. Lock the individual packages a rebuild needs to write.

**Courtyard rails, entrance letters and hedges (#2325).** The export carries the RGBA rail texture from
`src/surroundings.js` on the A/B/C loggias and the courtyard-edge fence. The glTF uses the web's
0.5 alpha cutoff, double-sided panels and existing UVs. Hus L's loftgång and terrace balusters are
already geometry. The white A/B/C plates use the same letter atlas and each plate's original third
of the image. These materials have separate keys in the GLB so the importer can keep their images.

The patio hedge and entrance boxwood carry their grey leaf atlas multiplied in linear space by the
web's `clumpShade` and `CLUMP_MEAN`. Their UVs retain the configured leaf scale and clump diameters
(21 cm for patio hedges and 13 cm for boxwood). The export bakes a mirrored two-tile patch using a
side face as its reference. This is a *guess* for the static approximation of the web shader. The
tint, vertex shading, hedge shape and collision still come from the source mesh. The web adds
view-dependent fading, fine bump relief and stem shading near the base at render time.

`tests/check_site_details.py` (commandlet, `run-python.ps1`) reads these keys and the river keys from `Import/*.glb` and
fails when any of them falls back to another material in the world levels: the rails, letters and hedges must keep
Interchange's textured instance with the GLB's image size (rails masked and two-sided), the river keys their
`material-map.json` masters. Results and picture pairs: [#2325 verification](../verification/2325/README.md).

**Grass (#2308).** The web has no grass geometry: its lawns are the ground meshes with `src/grass.js`'s detail map. The
export names each material's colour map (`measurements.json` `materials[].map`, `shared-grass-detail` on the lawns), and
`material-map.json` maps the two lawn keys (`std_609548_r100_m0_tex`, GRASS.summer; `std_5f8a3e_r100_m0_tex`, the street
lawns) to `MI_LundenGrassLawn` / `MI_LundenGrassStreet` of the master `M_LundenGrass` ([Surface materials](#surface-materials-2282)):
the canvas map rebuilt in UV metres (blade strokes, dry and lush patches, tussock bases) from `GRASS`'s numbers,
checked by `tests/grass-material.test.mjs` (Node, against `src/config.js`) and `test_materials.py` (every lawn key of
the export on a grass instance with its own colour). The lawn master uses `MPC_LundenVegetation.Month` and
the web's twelve `GRASS.autumnMix` values to mix each instance's summer colour towards `GRASS.autumn`.
The shader approximates the canvas detail and its response to lighting (*guess*).

For the optional offscreen perennial motion check, set `LUNDEN_VEGETATION_RENDER=1` and run the same PIE test

`BP_LundenSky` drive 0 and 13 m/s, then compares its depth silhouette across game frames. The change in wind must
exceed the calm control. `Saved/vegetation-result.json` includes the pixel counts under `perennialMotion`.

### Generated assets: rebuilt, not versioned (decided)

The three zones import to **249 MB** (248,848,382 bytes) (l1007: StaticMeshes 166 MB, Materials 35 MB, SceneImport asset 30 MB, level
6 MB). A re-import writes every package anew (new GUIDs), so each import that is committed stores the full size again
in Git LFS (GitHub Free: 10 GiB storage, 10 GiB download per month). **Recommendation: do not version generated
assets**; every Unreal checkout rebuilds them (export ≈ 2 min, import ≈ 2 min), and packaging (#2248) runs export +
import before cooking. `/Content/Lunden/Generated/` is Git-ignored. Hand-made content that
references generated assets (#2246 levels/Blueprints) would then reference them by path/tag, which the stable ids
make possible. **Decision (#2245, 2026-11-20; can be overturned in one sentence):** they are not versioned and
`/Content/Lunden/Generated/` stays Git-ignored. Alternatives if that changes: version them in LFS (budget ≈ 250 MB
per committed import), or shrink first (drop the `InterchangeSceneImportAsset`, decimate the heaviest furniture) and
re-measure.

### Screenshots

`tools/unreal-engine/python/screenshot_level.py <out dir> [zone]` renders fixed views of an imported level with a
SceneCapture2D and temporary sun/sky light (nothing is saved). It needs the GPU: run `UnrealEditor-Cmd.exe` directly
with `-run=pythonscript -AllowCommandletRendering` (commandlets otherwise load NullDrv and every render target is
"released"); `run-python.ps1` always passes `-nullrhi`. The first GPU run compiles the editor's SM6 shaders (about
20 minutes on the development PC, cached in the DDC afterwards; later runs take 20 s). The script waits for mesh and
shader compilation (`AutomationLibrary.finish_loading_before_screenshot`), hides the collision boxes (hidden in game
only, so an editor-world capture would draw them) and renders without Lumen and virtual shadow maps, which need many
frames to converge.

